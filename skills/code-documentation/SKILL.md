# 代码库文档与入门维护

分析软件项目，建立代码库上下文，并生成、改进和维护准确、可用、与代码同步的文档。使用这个技能时，先理解真实代码、项目结构和既有约定，再决定应该新增、更新或保留哪些文档和项目级指令。

这个技能同时覆盖两类需求：帮助人和 Codex 快速理解陌生代码库，以及让 README、API 文档、架构文档、开发者指南、changelog、代码注释和 `AGENTS.md` 持续反映当前代码。

## 核心能力

- 分析陌生代码库，产出入门指南、架构地图、关键入口、目录职责和项目约定。
- 生成或更新项目级 `AGENTS.md`，并从 `CLAUDE.md` 迁移仍适用于 Codex 的项目约定。
- 生成或更新 `README.md`、API Reference、架构文档、开发者指南、贡献指南、changelog 和迁移指南。
- 根据代码分析补充函数、类、模块、CLI、配置项、环境变量、权限和错误处理说明。
- 为 Python、TypeScript/JavaScript、Go、Rust、Java、C/C++ 等代码补充符合生态习惯的注释。
- 在修改或新增功能后执行文档影响检查，避免代码与文档漂移。

## 使用场景

根据用户目标选择最小足够流程：

- **入门分析**：用户要求理解陌生仓库、生成项目地图、梳理架构、识别关键入口，或生成/更新 `AGENTS.md`。
- **文档生成**：用户要求 README、API 文档、架构说明、开发者指南、贡献指南、changelog、迁移指南或代码注释。
- **代码变更交付**：本轮修改或新增功能后，检查是否影响用户可见行为、API、配置、命令、架构、数据模型、权限、错误处理或部署方式，并更新相关文档。

如果用户只要求临时生成一段独立说明或注释，不要主动创建 `AGENTS.md`；但如果本技能用于项目级分析、项目文档维护或代码库入门，应检查并生成/更新目标项目根目录的 `AGENTS.md`。

## 工作流程

### 阶段 1：代码库入门与项目上下文建立

先收集足够信号，不要读取整个仓库。优先使用 `rg`、`rg --files`、目录快照和清单文件。只在信号不明确时选择性读取源码。

#### 1.1 项目侦察

并行检查这些项目事实：

| 信息 | 检查位置 |
| --- | --- |
| 项目清单 | `package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`、`pom.xml`、`build.gradle`、`Gemfile`、`composer.json` |
| 框架指纹 | `next.config.*`、`nuxt.config.*`、`angular.json`、`vite.config.*`、Django settings、Flask app factory、FastAPI main、Rails config |
| 入口文件 | `main.*`、`index.*`、`app.*`、`server.*`、`cmd/`、`src/main/` |
| 目录结构 | 顶层和前两层目录，忽略 `.git`、`node_modules`、`vendor`、`dist`、`build`、`__pycache__`、`.next` |
| 配置与工具 | `.eslintrc*`、`.prettierrc*`、`tsconfig.json`、`Makefile`、`Dockerfile`、`docker-compose*`、`.github/workflows/`、`.env.example` |
| 测试结构 | `tests/`、`test/`、`__tests__/`、`*.spec.*`、`*.test.*`、`*_test.go`、`pytest.ini`、Jest/Vitest/Playwright 配置 |

#### 1.2 架构映射

基于侦察结果识别：

- 技术栈：语言版本、框架、主要库、数据库、ORM、构建工具、CI/CD。
- 架构形态：单体、monorepo、微服务、serverless、前后端分离、全栈应用或纯后端服务。
- API 风格：REST、GraphQL、gRPC、tRPC、CLI、SDK 或其他。
- 关键目录：只记录会影响开发路径的目录，不解释显而易见的目录名。
- 典型数据流：从入口、校验、业务逻辑、数据访问、外部服务到响应、错误或副作用。

#### 1.3 项目约定识别

记录已经存在的模式，不要凭空发明标准：

- 命名约定：文件、组件、类、函数、服务、hook、模块和测试文件命名。
- 代码模式：错误处理、依赖组织、状态管理、异步方式、配置来源。
- Codex 工作约束：安装、开发、测试、lint、build、迁移、代码生成和交付前检查命令。
- 修改边界：源码目录、生成文件、构建产物、外部同步文件、危险命令和外部依赖。
- Git/PR 约定：能从历史可靠判断时记录分支命名、commit message 和 PR 工作流；历史不可用时标注未知。

#### 1.4 文档侦察

检查这些位置，并记录它们分别承担什么职责：

- `README.md`
- `docs/`
- `CHANGELOG.md`
- `CONTRIBUTING.md`
- `AGENTS.md`
- `CLAUDE.md`
- `examples/`
- OpenAPI/Swagger、GraphQL schema、TypeDoc、Sphinx、MkDocs、Docusaurus 等生成源
- 源码中的 public API 注释、模块说明和示例代码

已有文档存在时，优先增量更新；除非用户明确要求重写，不要整体替换。

### 阶段 2：建立或更新 `AGENTS.md`

当本技能用于项目级分析、项目文档维护或代码库入门时，必须检查目标项目根目录的 `AGENTS.md`。

#### 2.1 更新规则

- 如果项目没有 `AGENTS.md`，创建最小项目级指令文件。
- 如果项目已有 `AGENTS.md`，先读取并增量增强，保留已有项目特定要求。
- 如果项目没有 `AGENTS.md` 但有 `CLAUDE.md`，读取 `CLAUDE.md`，只迁移仍适用于当前项目和 Codex 工作流的项目约定，不复制 Claude 专属表述。
- 如果用户明确禁止修改项目文件，只输出建议写入 `AGENTS.md` 的内容和理由。

#### 2.2 必须写入的高优先级规则

在 `AGENTS.md` 靠前位置加入或维护这一规则，建议放在 `## 高优先级规则` 或 `## 交付要求` 下：

```markdown
## 高优先级规则

- 修改或新增功能后，如果影响用户可见行为、API、配置、命令、架构、数据模型、权限、错误处理或部署方式，必须检查并同步更新相关项目文档，包括 README、docs、API 文档、配置说明、示例、changelog 或迁移指南。若判断无需更新文档，交付回复中必须说明依据。
```

#### 2.3 `AGENTS.md` 最小结构

项目级 `AGENTS.md` 应简洁记录：

- 高优先级规则。
- 技术栈。
- 构建与运行命令。
- 测试和交付前检查。
- 代码风格和项目约定。
- 项目结构和关键入口。
- 修改边界和危险操作。
- 未知项。

### 阶段 3：确定产物范围

根据任务类型和项目规模选择最小足够产物：

| 任务或规模 | 推荐产物 |
| --- | --- |
| 入门分析 | 对话中的入门指南 + 项目级 `AGENTS.md` |
| 单文件脚本 | 文件头使用说明 + 必要内联注释 |
| 小型库 | README + 公开 API 说明 + 最小示例 |
| 中型项目 | README + API 文档 + 示例 + 开发设置 |
| 大型项目 | README + 架构文档 + API 文档 + 贡献指南 + changelog |
| 代码变更交付 | 只更新受影响的既有文档，并在最终回复说明文档检查结果 |

不要为了“完整”新增不必要的文档文件。优先更新项目已经采用的文档结构。

### 阶段 4：生成或更新入门与项目文档

#### 入门指南

当用户要求理解代码库或 onboarding 时，在对话中输出结构化入门指南：

- 概览：项目做什么、服务谁、主要能力是什么。
- 技术栈：语言、框架、数据库、ORM、测试和构建工具。
- 架构：组件如何连接，必要时用简短文本图或 Mermaid。
- 关键入口：API、页面、CLI、数据库、配置和任务脚本。
- 目录地图：顶层目录到职责的映射。
- 请求生命周期或数据流：追踪一条典型路径。
- 项目约定：命名、错误处理、测试模式、Git/PR 工作流。
- 常用任务：开发、测试、lint、构建、迁移。
- 修改入口：不同类型改动应查看的位置。

#### README

README 应覆盖：

- 项目是什么，解决什么问题。
- 核心能力或特性。
- 前置条件和安装方式。
- 最小可运行示例。
- 配置项、环境变量或运行参数。
- 常用开发命令：启动、测试、lint、构建。
- API、架构、示例、贡献指南等进一步文档入口。
- License 或项目已有的许可说明。

#### API 文档

为每个公开 API 记录：

- 名称和签名。
- 参数、类型、是否必填、默认值。
- 返回值。
- 可能抛出的错误或错误码。
- 副作用、权限要求或性能注意事项。
- 至少一个可运行或贴近真实用法的示例。

参数、配置项和错误码优先用表格表达。不要猜测签名或行为，以源码、schema、测试和示例为准。

#### 架构文档

中大型项目或架构变化时，记录：

- 系统边界和主要组件。
- 关键入口、目录职责和依赖关系。
- 一条典型请求、命令或数据流。
- 重要设计决策、取舍和约束。
- 必要时使用简短 Mermaid 图，但不要用图替代文字说明。

#### 内联代码文档

只给公开、复杂或容易误用的代码补充注释。避免解释显而易见的实现。

| 语言 | 推荐格式 |
| --- | --- |
| Python | Google 风格 docstring，遵循 PEP 257 |
| TypeScript/JavaScript | TSDoc/JSDoc |
| Go | GoDoc，导出标识符注释以名称开头 |
| Rust | Rustdoc `///` |
| Java | Javadoc |
| C/C++ | Doxygen |

### 阶段 5：代码变更后的文档交付门禁

当本轮任务包含代码修改、新增功能、行为变更或配置变更时，交付前必须执行这一检查。

#### 5.1 影响范围

如果改动影响以下任一项，必须检查并同步更新相关文档：

- 用户可见行为。
- 公开 API、SDK、schema、类型声明或示例。
- 配置项、环境变量、默认值或部署方式。
- CLI 命令、参数、脚本、安装、运行、测试或构建方式。
- 架构、目录职责、请求流、数据流或外部依赖。
- 数据模型、数据库 schema、迁移或权限模型。
- 认证、授权、安全行为、错误码、异常处理或故障排查方式。

#### 5.2 文档映射

| 代码或行为变化 | 应检查的文档 |
| --- | --- |
| 新增/修改公开 API | API Reference、README 示例、OpenAPI/GraphQL schema |
| 新增 CLI 命令或参数 | README、CLI docs、帮助文本、示例 |
| 新增配置项或环境变量 | README、配置文档、`.env.example`、部署文档 |
| 修改安装、运行、测试或构建方式 | README、开发者指南、CI 文档 |
| 修改架构、目录职责或数据流 | 架构文档、开发者指南、`AGENTS.md` |
| 修改数据库 schema、迁移或数据模型 | 架构文档、迁移指南、开发者指南 |
| 修改权限、认证、错误码或安全行为 | API 文档、用户可见说明、运维文档 |
| 新增用户可见功能或移除功能 | README、功能说明、changelog、迁移指南 |

#### 5.3 交付要求

- 如果文档已经覆盖且仍准确，在最终回复中说明“不需要更新文档”的依据。
- 如果文档过时或缺失，优先更新最近、最权威的既有文档。
- 如果没有合适文档，只有在信息对用户或维护者必要时才新增最小文档。
- 若用户明确要求本轮不要修改文档，只输出应更新的文档清单和理由。

### 阶段 6：质量检查

交付前检查：

- 文档描述与当前代码一致。
- 示例使用真实存在的函数、类、命令、路径和参数。
- 新增或修改的公开 API 都有说明。
- 配置项、环境变量和默认值没有遗漏。
- 内部链接、相对路径和引用文件存在。
- `AGENTS.md` 保留已有项目特定要求，并包含文档交付门禁。
- 术语、标题层级、表格格式和语气保持一致。
- 文档语言跟随项目现有文档；如果没有现有文档，中文用户场景默认使用中文。

## 写作原则

1. 先说明为什么存在，再说明如何使用。
2. 从最小可运行示例开始，再逐步展开复杂场景。
3. 优先给示例和表格，少写空泛说明。
4. 使用主动语态和现在时。
5. 函数名、路径、命令、变量和配置项使用代码格式。
6. 不确定的事实要标注，不要写成确定结论。
7. 保留项目已有文档风格，除非用户要求统一重构。

## 输出方式

- 优先更新项目内既有文档文件。
- 多文件文档应保持项目已有目录结构。
- 生成新文档前先确认是否已有同类文档可以增量更新。
- 最终回复说明：更新了哪些文档、为什么更新、是否更新或检查了 `AGENTS.md`、是否还有未处理的文档风险。
- 如果只做分析不改文件，输出受影响文档清单、判断依据和建议更新内容。

## 注意事项

- 始终先看真实代码、配置、测试和已有文档，再写文档。
- 不要凭经验补全不存在的 API、命令或配置。
- 不要把生成文件、构建产物或外部同步文档当作首选编辑目标。
- 不要生成超过必要长度的 `AGENTS.md`；除非项目确实复杂，否则保持在 100 行以内。
- changelog 推荐使用 Keep a Changelog 的结构，但遵循项目已有格式优先。
- 大型项目先覆盖公开 API、关键入口和高频开发路径，再扩展到细节。
