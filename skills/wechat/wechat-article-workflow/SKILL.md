# 公众号文章工作流

把这个 skill 当成公众号文章生产的 harness 使用，不要当成一次性的写作提示词。它的目标是帮助用户把素材和真实工作过程变成一篇可发布的文章，同时保留用户自己的判断、语气、归因、截图和可复用资产。

## 核心规则

### 写作判断优先

- 文章目的先于写作任务和文章外壳。必须先判断用户写这篇文章是为了教学、复盘、展示效果、引流转化、表达判断，还是其他明确目的；目的不清楚时，不能假装已经清楚。
- 先判断文章目的、写作任务、读者状态、主承诺和证据，再选择文章外壳。不要先套“案例/教程/复盘/观点”模板。
- 如果任务涉及 AI 工具、工作流、技术案例、企业 AI 应用、前端 / AI 编程、Prompt、Skill、MCP、个人效率或公众号方法文，在判断文章目的和写作任务后读取 `references/benchmark-writing-system.md`，按文章任务、文章外壳和证据条件选择结构和对标方法。
- 信息排序服务读者的认知路径，不服务素材顺序或流程完整性。
- 开头只负责让读者继续读；结尾只负责让文章在读者心里多停留一下。不要写机械背景和机械总结。
- 做减法和做加法同等重要。没有读者收益、证据或认知推进的内容，删除或并入素材笔记。

### 事实和归因边界

- 保留用户的真实判断。不要把用户自己做的决策过度归因给 AI、Codex 或某个 skill。
- 优先写具体过程、截图、提示词、对话、文件和决策。不要用漂亮但空泛的文字掩盖证据缺失。
- 缺少真实对话、截图、数字、结果或选择理由时，保留明确占位，不编造。

### 作者人设不变

- 作者人设的唯一来源是 `references/author-persona.md`。不要在其他文件里另立人设规则。
- 不要仿写具名作者。只能吸收清晰、节奏、真实技术叙述这类宽泛特征。
- 使用最小切片修改。用户指出“不对”时，先定位是章节、段落、标题、图片还是归因问题，不要默认整篇重写。

### 外部 skill 门禁

- 在检查点停下来。AI 可以推荐，但不能偷偷替用户做关键决策。
- 用户回答检查点问题，只代表补充信息，不代表确认进入下一阶段。只有用户明确说“确认大纲”“开始初稿”“继续写初稿”等授权语句，才允许从阶段 3 进入阶段 4。
- 检查点反馈改变文章目的、写作任务、读者状态、主承诺、章节顺序、素材边界、归因边界或对标边界时，必须先更新对应文件并再次摘要展示变化，再等待确认。
- 凡是公众号封面、顶图、底图、Axu/Xukache 风格正文插图、生成式配图提示词，必须使用 `axu-article-illustrations`。不得自行用 HTML、SVG、CSS 或临时页面生成视觉资产，除非用户明确要求。
- 凡是把最终 Markdown 转成公众号可复制富文本、内联样式 HTML、阿栩品牌排版或打开公众号排版编辑器，必须使用 `wechat-axu-styler`。它只做排版导出，不改写文章结构，不生成图片，不替代 `axu-article-illustrations`。
- 长期偏好和单篇文章状态要分开管理。见 `references/memory-management.md`。

## 工作流程

### 阶段 0：输入识别

识别用户提供了什么：

- 主题或粗略想法
- 素材、项目文件夹、截图、链接、AI 对话记录
- 已指定的写作任务或文章外壳
- 已存在的文章目录或草稿
- 是否需要配图
- 用户当前要做的是起草、修改、续写、review 还是交付整理

如果任务不清楚，只问一个关键问题。否则基于合理假设继续，并说明假设。

### 阶段 1：素材地图

写作前先阅读相关本地文件。建立素材地图：

- 必须保留的事实
- 用户决策和已确认归因
- 已有截图或图片
- 缺失素材或对话占位
- 约束，例如“不要改顶图和底图”

用户提供的原始素材要统一放入文章目录下的 `raw-materials/` 文件夹，例如对话记录、代码文件、截图、链接摘录、网页资料、参考文章和用户手写笔记。后续写稿时优先从这个文件夹建立素材地图。

素材很大时，只总结有用部分，不要把全部内容塞进文章。

### 阶段 2：文章目的、写作任务、读者状态和文章承诺

使用 `references/article-types.md` 先判断文章目的：教学、复盘、展示效果、引流转化、表达观点，或用户给出的其他目的。文章目的决定结构、证据类型、结尾动作和是否需要教程步骤、前后对比或获取方式。

文章目的必须由用户确认或明确接受建议。用户没有说明目的时，可以给出一个建议目的，但必须在检查点 1 展示，不得静默替用户决定。

再判断写作任务：解释、教学/实操指导、说服、共鸣、决策支持或记录复盘。写作任务决定开头、重点、证据和结尾。

如果主任务或辅助任务包含解释，继续判断技术解释子类型：概念解释、原理拆解、代码讲解、机制对比或实现拆解。不要把安装教程、架构拆解、代码实现都写成同一种解释文。

再判断读者当前状态：他知道什么、困惑什么、为什么会点开、读完后最可能做什么。涉及用户长期写作风格、人设、概念解释或表达取舍时，同时读取 `references/author-persona.md`。

最后选择文章外壳：观点、教程、案例、技术复盘或混合型。文章外壳只服务写作任务，不反过来支配文章。

如果文章主题属于 AI 工具、工作流、技术案例、企业 AI 应用、前端 / AI 编程、Prompt、Skill、MCP、个人效率或公众号方法文，读取 `references/benchmark-writing-system.md`，完成“对标融合选择”：

- 这篇主借智见AI、主借韦东东、主借大前端架构师，还是按能力分工。
- 借的是标题、开头、结构、解释、证据还是结尾。
- 哪些东西明确不借，尤其是具名作者人格、夸张口吻、客户案例、工程权威感、前端架构师身份、软考分支和未经验证的资源堆叠。
- 当前素材是否满足所选结构的证据门槛。

选择结构前必须做价值筛选：确认文章主承诺、读者能拿走什么、哪些素材必须保留、哪些素材虽然存在但不进入正文主线。不要为了完整展示流程而铺满所有章节。

### 阶段 3：大纲

完整初稿前先产出大纲，并写入文件。不要只在会话中展示大纲。大纲要遵守 `references/author-persona.md` 的作者人设和价值筛选规则。大纲应包含：

- 工作标题
- 文章目的：教学、复盘、展示效果、引流转化、表达观点，或用户指定的其他目的
- 写作任务
- 技术解释子类型，如果包含解释任务
- 目标读者和读者当前状态
- 文章承诺
- 对标融合选择，如果适用：主参考方法、借什么、不借什么、证据门槛
- 开头策略：认知缺口、共鸣场景、结果前置或冲突
- 读者认知路径
- 最关键的一节，以及为什么它应获得最多篇幅
- 章节列表
- 每节要证明什么
- 每节读者能拿走什么
- 每节用哪些具体素材支撑
- 哪些素材要删除、合并或只放进素材笔记
- 抽象概念是否需要类比或例子解释
- 如果是教学/实操指导：前置条件、预期输出、验证方式和常见错误
- 哪些章节需要截图、提示词或 AI 对话
- 已知归因边界

如果最终标题尚未确认，先使用工作标题或安全短名创建临时文章目录，例如 `articles/<工作标题>/outline.md`；标题确认后再按 `references/output-structure.md` 统一整理或重命名。

除非用户明确要求跳过确认，否则在检查点 1 停下来。

检查点 1 必须按 `references/workflow-checkpoints.md` 输出“待确认决策表”。不要只说文件已写入，也不要把用户补充信息当成进入初稿的授权。

检查点 1 的首要决策是文章目的。用户只回答素材、问题或偏好，不等于确认文章目的；如果文章目的仍可能有多种解释，必须继续停在大纲阶段。

### 阶段 4：初稿

只有用户明确确认大纲并授权进入初稿后，才写完整初稿。写稿时使用 `references/writing-style.md` 和 `references/author-persona.md` 控制表达，不要把用户风格写成通用 AI 教程腔。真实细节缺失时要明确标注用户需要补充的位置：

如果大纲包含对标融合选择，写稿时同时使用 `references/benchmark-writing-system.md`：

- 智见AI只用于标题承诺、开头痛点、概念转译和短段节奏。
- 韦东东只用于技术链路、工程证据、选型边界、bad case 和验证逻辑。
- 大前端架构师只用于前端 / AI 实操场景、清单资产、完整提示词或指令模板、AI 编程翻车复盘和检查清单收束。
- 任何没有真实证据的强判断都降级为条件判断或占位。
- 不模仿具名作者口吻，不写用户没有经历过的项目和结果。

- 真实 AI 对话
- 需要截图的位置，尤其是项目页面、HTML 预览、生成结果或文件结构
- 用户自己的选择理由
- 准确提示词或命令
- 数字、日期、文件名和结果证据

初稿完成后，按 `references/writing-style.md` 做删减测试、替换测试、出声测试、So what 测试和 AI 味测试。

初稿完成后，必须额外做“目的匹配检查”：

- 如果目的是教学：是否真的能让读者照着做出可验证结果？
- 如果目的是复盘：是否写清触发原因、真实过程、关键转折、修正和心得，而不是文件说明书？
- 如果目的是展示效果：是否有前后对比、截图、数据或样例证据？没有证据时必须降级表达。
- 如果目的是引流转化：是否写清资产能解决什么、适合谁、不适合谁、如何获取，并避免硬广腔？
- 如果目的是表达观点：是否有清晰判断、论据、边界和读者行动建议？

结构和文章目的不匹配时，先改初稿，不进入标题阶段。

如果 `visual-plan.md` 中的截图、对话或文件证据用于支撑正文关键判断，`draft.md` 对应段落必须插入截图占位、对话占位或规则摘录占位，不能只写在 `visual-plan.md`。

初稿必须检查大纲中标记的“最关键的一节”是否真的获得最多篇幅、最多证据和最清晰结构。没有兑现时，先改初稿，不进入标题阶段。

### 阶段 5：协助用户改写

当用户逐段改写或提出反馈时：

- 尽量保留用户更锋利、更自然的表达
- 压缩重复解释
- 保留具体案例和对话
- 修结构，但不要把个性磨掉
- 继续维护归因边界

不要把用户改得更鲜活的段落重新改回 AI 腔。

完成用户当前修改后，按 `references/memory-management.md` 判断这条反馈是否需要写入单篇交接文档的“可沉淀规则候选”。不要在修改前打断用户，也不要每条修改都询问沉淀。

如果反馈涉及“这不像我”“太抽象”“没有价值”“看不懂”“不是我的风格”，按 `references/author-persona.md` 的纠错分类处理：先修当前文章，再判断是否更新作者人设或写作风格规则。

### 阶段 6：标题

只有在草稿方向稳定后，才生成 10 组主标题和副标题。使用 `references/writing-style.md` 的口吻规则。标题方向要有差异：

- 直接案例复盘
- 结果导向
- 适度好奇心，不夸大
- 个人 IP 角度
- 技术工作流角度

如果文章使用对标融合选择，同时参考 `references/benchmark-writing-system.md` 的标题公式。标题可以借清晰承诺和冲突感，但必须降夸张强度，并确保正文有证据兑现。

让用户选择或修改最终标题，再用于目录名、封面文字或最终文件名。

### 阶段 7：配图计划

使用 `references/visual-workflow.md`。配图计划是动态文件，不是开头生成后就固定不变。初稿确认、用户改稿、标题变化、素材补充后，都要更新 `visual-plan.md`。

每个图片位置都要判断属于哪一种：

- 已有图片
- 需要截图
- 生成提示词占位
- 固定顶图/底图
- 仅封面使用，不插正文

如果用户提供了项目链接、本地 HTML、预览页面或可运行结果，优先考虑从项目页面截图来丰富文章证据。对话记录如果已经有原始文本文件，优先从文本中摘录，不默认要求对话截图。

凡是公众号封面、顶图、底图、Axu/Xukache 风格正文插图、生成式配图提示词，必须调用 `axu-article-illustrations`，并遵守它的固定资产和封面规则。HTML、SVG、CSS 或临时页面只能用于已有页面截图或用户明确要求的排版预览，不能替代配图 skill。

### 阶段 8：交付整理

使用 `references/output-structure.md`，把文章整理到 `articles/<最终标题>/` 下。保留草稿、大纲、配图计划、最终 markdown、图片、封面文件和交接文档。

最终 markdown 必须按 `references/output-structure.md` 补齐发布结构：

- 正文末尾罗列参考链接。只列真实使用过的链接、文档、项目、论文、工具页或素材来源；没有链接时写“本文无外部参考链接”，不要编造。
- 固定底图之后增加 `#tag` 标签行。标签从文章内容自动识别，优先选择大流量、可检索、和正文强相关的热词，不超过 5 个。

交付收尾时，按 `references/memory-management.md` 提炼“可沉淀到 skill 的规则候选”。先写入单篇文章交接文档，只有用户确认这是长期偏好后，才更新 skill references。

如果本篇使用了对标融合选择，在交接文档记录实际采用的文章类型、结构来源、有效规则和需要纠偏的地方，供后续更新 `benchmark-writing-system.md`。

### 阶段 9：公众号排版导出

只有最终 Markdown 已经存在，并且用户需要公众号格式、富文本复制、阿栩品牌排版或发布前 HTML 预览时，才进入本阶段。不要在大纲、初稿或配图阶段提前做排版导出。

使用项目级 `wechat-axu-styler` skill。默认把最终 Markdown 转成阿栩品牌公众号 HTML：

```bash
node .codex/skills/wechat-axu-styler/scripts/convert.mjs articles/<最终标题>/<最终标题>.md
```

如果用户指定输出路径，使用：

```bash
node .codex/skills/wechat-axu-styler/scripts/convert.mjs articles/<最终标题>/<最终标题>.md --output articles/<最终标题>/<最终标题>_xukache_wechat.html
```

如果用户想视觉微调、复制富文本或现场编辑，打开本地编辑器：

```bash
node .codex/skills/wechat-axu-styler/scripts/open-editor.mjs articles/<最终标题>/<最终标题>.md
```

边界：

- `wechat-axu-styler` 只处理最终 Markdown 到公众号 HTML 的排版转换。
- 不用它修改文章目的、大纲、正文结构、标题、参考链接或标签。
- 不用它生成封面、顶图、底图、正文插图或生成式配图提示词。
- 不把 HTML、CSS、SVG 或临时页面当成插图生成方案。视觉资产仍然走 `axu-article-illustrations`。

完成后必须确认：

- HTML 文件存在。
- 输出文件名和 `references/output-structure.md` 约定一致，默认是 `<最终标题>_xukache_wechat.html`。
- 如果本次打开了编辑器，确认预览非空。
- 交接文档记录 Markdown 文件、HTML 文件、是否打开编辑器、剩余手动复制或发布动作。

最终回复前，按 `references/review-checklist.md` 做检查。

## 完成标准

只有当前请求的阶段真正完成，并且用户知道下一步做什么，才算完成。完整文章生产的完成标准是：
