# 需求阶段 Worker 标准

在 `pm-workflow` 阶段 1 使用本文档。目标是让需求阶段像资深产品经理工作，而不是机械收集功能点。

需求阶段必须先判断：用户到底卡在哪里、是否值得做、哪些需求进入清单、哪些需要验证、哪些应该后置或不做。没有完成需求 worker 产出和主 PM 验收，不得进入 MVP 范围、交互架构或原型设计。

## 主 PM 与需求 Worker 分工

- 主 PM：负责理解上下文、派发需求 worker、整合 helper skill 结果、追问用户、验收需求阶段产物。
- 需求 worker：负责基于用户输入和全局 helper skills 产出问题陈述、JTBD、是否值得做判断、需求清单、风险/验证清单。
- 主 PM 不得把需求 worker 的输出原样交付；必须审核、修正、标注假设，并用业务语言向用户确认。

## 子 Agent 调度规则

每个产品迭代第一次进入需求阶段时，主 PM 必须新开真实需求 worker。阶段内补充、调整、返工时复用已启动的需求 worker，不再重复新开。

需求 worker 的任务说明必须包含：

- 用户原始诉求和补充上下文。
- 当前已知事实与假设。
- 要调用的 helper skills。
- 本阶段必须输出的结构。
- 不允许进入原型、PRD、技术方案或排期。

只有在当前工具环境不支持新开 worker，或用户明确要求不要新开时，才允许降级为同一模型内的角色化流程，并在 `notes/requirements.md` 记录：

- 未派发真实 worker 的原因：工具不支持 / 用户明确禁止 / 其他。
- 如果是阶段内调整，记录复用了哪个已启动 worker。
- 采用的角色化 worker 流程。
- 使用和未使用的 helper skill。
- 主 PM 验收结论。

## 阶段引用白名单

需求 worker 只能读取以下输入：

- `references/demand-worker-standards.md`。
- 全局 `problem-statement` skill。
- 全局 `jobs-to-be-done` skill。
- 全局 `discovery-interview-prep` skill。
- 全局 `pol-probe` skill。
- 全局 `user-story` skill。
- 全局 `user-story-splitting` skill。
- 全局 `epic-breakdown-advisor` skill。
- 全局 `prd-development` skill。
- 用户提供的原始上下文、补充回答和已确认材料。

需求 worker 不得读取或套用以下阶段文档：

- 交互架构、菜单、页面结构相关 reference。
- 原型设计、主题选择、HTML 模板、PRD 浮标相关 reference。
- Impeccable 打磨、视觉审查、UI 质量相关 reference。
- 生产级 PRD、开发交接、流程图 viewer、artifact 交付相关 reference。

如果用户明确要求参考竞品、开源框架或行业最佳实践，需求 worker 只能把外部信息转成待验证假设、风险、后置项或验证动作，不得直接扩展 MVP 范围。

## 需求阶段必须调用的 Helper Skills

8 个技能都必须先从 `subskills/` 同步到全局 skills 目录，再按正常 skill 名称调用。不是每次全量调用；需求 worker 必须记录“已用 / 未用 / 未用原因”。

| Helper skill | 何时使用 | 作用 | 是否必用 |
| --- | --- | --- | --- |
| `problem-statement` | 需求模糊、用户先讲方案、老板意见或一句话想法 | 重写问题，明确用户、目标、阻碍、原因和影响 | 模糊需求必用 |
| `jobs-to-be-done` | 用户只讲功能、页面或模块 | 把功能语言拉回真实任务、痛点和收益 | 功能诉求必用 |
| `discovery-interview-prep` | 证据不足、需要访谈/调研/验证 | 设计访谈目标、对象、问题和反偏误方式 | 需要证据时用 |
| `pol-probe` | 是否该做不确定、风险高、想先验证 | 设计最小验证探针，避免直接开发 | 高风险假设必用 |
| `user-story` | 需求清单要进入可交付表达 | 把需求转成角色、动作、结果和验收场景 | 进入清单时用 |
| `user-story-splitting` | 需求太大，一个迭代吃不下 | 拆成更小、更安全的交付切片 | 大需求时用 |
| `epic-breakdown-advisor` | 复杂 Epic、后台系统、长流程、多角色协作 | 拆主干、依赖和 MVP 切片 | 复杂需求时用 |
| `prd-development` | 需求阶段结束前做准备度检查 | 检查是否具备进入正式 PRD 的信息基础 | 阶段验收时用 |

## 需求清单标准

需求阶段结束前必须输出需求清单，并让用户确认。需求清单不是功能列表；每条需求都必须说明问题、用户任务、价值、是否值得做和验收信号。

`requirements-list.md` 至少包含：

- 需求编号。
- 用户/角色。
- 问题陈述。
- JTBD。
- 用户目标。
- 功能候选。
- 价值/痛点代价。
- 证据等级。
- 是否值得做：做 / 先验证 / 后置 / 不做。
- 优先级。
- 进入一期原因。
- 依赖与风险。
- 验收信号。
- 使用的 helper skill。

## 主 PM 验收门槛

主 PM 必须逐项检查：

- 没有问题陈述，不进入需求清单。
- 没有 JTBD，不把功能诉求当成需求。
- 没有“是否值得做”判断，不进入 MVP 范围。
- 没有需求清单，不进入交互架构或原型设计。
- helper skill 未调用且未记录原因，不允许完成需求阶段。
- 如果判断为“先验证”，必须给出验证动作或说明为什么暂不验证。
- 如果判断为“后置”或“不做”，必须说明原因，避免后续又偷偷进入原型。

## 用户确认输出

主 PM 给用户的需求阶段确认输出必须包含：

- 问题定义摘要。
- 是否值得做判断摘要。
- 需求清单表。
- 暂不做/先验证/后置项。
- helper skill 使用记录摘要。
- 下一步：确认后才进入范围表和交互架构。
