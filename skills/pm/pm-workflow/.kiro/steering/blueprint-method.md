# 五层递进蓝图法(blueprint 阶段方法论)

> 从「需求澄清完成」到「UI 开始动手」之间的桥梁。把产品的**结构**(给谁用、怎么用、有哪些页、怎么跳、有哪些功能、怎么交互)按五层逐层敲定,得到一份逐层确认的**设计底稿**,作为 UI 高保真的直接输入。

## 何时使用

- 入口:`docs/workflow-state.json.clarification.status=user_confirmed` 之后,`design` 阶段开始之前。
- 推荐顺序下:`init → blueprint → design → analyze(PRD) → architect → plan`。蓝图先于 UI 与 PRD,**让设计与成文都基于同一份逐层确认的结构**。

## 五层顺序与执行规则

**串行**,前一层不通过不进下一层。**层内一次只抛一项**(应用 craft-principles 第 1、2 条:一次只抛一项 + 决策三件套)。

### 第 1 层:信息架构(IA)

确认产品由哪些页面组成、谁会用、全局导航是什么、跳转怎么走。

产出:
- 页面清单表(P0/P1/...,页面名、给谁用、作用、频次)
- 全局导航(侧边栏/顶栏组成与规则)
- 跳转地图(`P0 → P1 → P2 …`)
- 每条决策一句**为什么这么定**

**通过条件**:用户对页面清单、导航与跳转地图都确认。

### 第 2 层:核心流程

把第 1 层的页面串成端到端流程,标出关键节点。

产出:
- 各类用户的端到端流程(从登录/触发到产出/结束)
- 关键节点位置(强制卡点 / 可选确认点)
- 不同用户类型的共性与差异

**通过条件**:用户对每条主流程都点过头,关键卡点位置已定。

### 第 3 层:逐个页面

每页的模块构成、布局选型、四态(正常/空/加载/错误)。

产出(每页):
- 骨架描述(顶部/主区/底部 或 左右栏)
- 布局选型(单列 / 双栏 / 网格 / Tabs / Steps),带选型理由
- 模块列表
- 四态描述

**通过条件**:每页都有骨架+布局选型理由+四态。

### 第 4 层:逐个功能

每个功能的输入、处理、输出、异常、MVP 边界,功能用 `M{模块号}-F{功能号}` 编号。

产出(每个功能):
- 输入 / 处理 / 输出
- 异常分支
- MVP 边界(本期做 / 二期做 / 不做)
- 待联调或业务定价的数值标「待定」,**不编造**

**通过条件**:所有 P0 功能都按 G/F 编号挂账,所有数值要么有依据要么标待定。

### 第 5 层:逐个交互

收口前面层挂账的交互点。聚焦交互逻辑与异常分支,不写像素级视觉(那是 design)。

产出:
- 关键交互点 I1/I2/...:触发 / 主流程 / 异常或边界
- 全局异常态(生成失败 / 网络断开 / 额度不足等)
- 等待反馈与冲突处理规则

**通过条件**:每个交互都有清晰的「触发-主流程-异常」三段;全局异常态有统一规范。

## 沉淀文件

`docs/feature-flow-layout.md`,分节对应:主骨架 / 信息架构 / 流程 / 页面 / 功能 / 交互 / 取舍 / 待确认。

## 与下游的接口

- **design 阶段**:直接读这份蓝图作为输入。design 不再做信息架构(已在第 1 层定),只做视觉系统、Tokens、HTML 原型、Impeccable 自审。
- **analyze 阶段(PRD 后置)**:基于已确认的蓝图与 design 产物**回填成文**,需求分析师不再凭空起草 PRD,而是把蓝图里的功能编号、规则、边界、流程编辑为 PRD 章节。
- **architect 阶段**:技术架构师以蓝图的页面清单、功能边界、交互逻辑作为接口与数据建模的依据。

## 重大变革协议(blueprint 内尤其重要)

用户在第 3-5 层提出"我想把流程改一下"时,**禁止顺手改**当前层。先按 craft-principles 第 4 条:验证洞察 → 梳理连锁影响 → 确认范围 → 全文一致传播 → 一致性检查。蓝图层之间耦合很紧,改第 2 层(流程)往往牵动第 3 层(页面)、第 4 层(功能)、第 5 层(交互)的多处挂账。
