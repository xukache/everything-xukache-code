## 示例 1：小任务提示词优化

**用户原始需求：** "帮我给 getUserById 加缓存"

**输出：**

### 判断的任务类型
实现

### 任务规模判断
小任务 → 直接优化提示词

### 优化后的提示词

```text
你是一个谨慎的资深软件工程师。请先阅读当前项目，不要直接修改代码。

任务：给 getUserById 增加缓存。

开始前请先：
1. 阅读 getUserById 的实现和调用方。
2. 阅读项目中是否已有缓存机制或工具函数。
3. 分析 getUserById 的调用频率和数据更新频率。

实现要求：
1. 使用内存缓存 Map，不要引入 Redis 或其他新依赖。
2. TTL 为 5 分钟。
3. 用户信息更新时清除对应缓存。

约束：
1. 只修改与 getUserById 直接相关的代码。
2. 不要改其他函数。
3. 不要改函数签名。
4. 保持现有错误处理风格。

完成后说明：
1. 修改了哪些文件。
2. 缓存命中 / 失效的逻辑。
3. 如何验证缓存生效。
```

### 补充的关键约束
1. 不引入新依赖
2. 不改函数签名
3. 只改最小范围

### 建议先让 AI 读取的上下文
1. getUserById 实现文件
2. 调用 getUserById 的文件
3. 项目中已有的缓存工具（如有）

## 示例 2：大需求拆解

**用户原始需求：** "给电商系统加购物车功能"

**输出：**

### 判断的任务类型
实现

### 任务规模判断
大需求 → 先拆解

### 任务拆解清单

| # | 层级 | 任务 | 依赖 | 完成标准 | 可并行 |
|---|---|---|---|---|---|
| 1 | 数据 | 创建 cart 和 cart_item 表，写 Migration | 无 | migrate up/down 成功 | - |
| 2 | 模型 | 创建 Cart 和 CartItem 的 ORM 模型 | 1 | 能 CRUD 购物车数据 | 否 |
| 3 | 服务 | 实现 CartService（addItem, removeItem, updateQuantity, getCart, clearCart） | 2 | 单元测试全部通过 | 否 |
| 4 | 接口 | 实现 REST API（5 个端点） | 3 | 接口测试通过，权限正确 | 否 |
| 5 | 集成 | 和订单模块对接（结算→创建订单→清空购物车） | 4 | 集成测试通过 | 否 |

### 推荐先执行的第一个任务提示词

```text
你是一个谨慎的资深软件工程师。请先阅读当前项目，不要直接修改代码。

任务：创建购物车相关的数据库表（cart 和 cart_item），并编写 Migration。

开始前请先：
1. 阅读项目中已有的 Migration 文件，了解写法和命名规范。
2. 阅读已有的数据库表结构，了解主键、外键、时间戳字段的风格。
3. 阅读 user 和 product 表结构（购物车需要关联用户和商品）。

要求：
1. cart 表至少包含：id、user_id、created_at、updated_at。
2. cart_item 表至少包含：id、cart_id、product_id、quantity、created_at、updated_at。
3. 设置正确的外键关系。
4. Migration 支持 up 和 down。

约束：
1. 不要修改已有表。
2. 保持项目现有 Migration 命名和写法风格。
3. 不要引入新依赖。

完成标准：
1. migrate up 成功创建表。
2. migrate down 成功删除表。
3. 不影响现有数据库结构。
```

## 示例 3：Bug 修复提示词优化

**用户原始需求：** "登录接口有时候返回 500"

**输出：**

### 判断的任务类型
修复

### 任务规模判断
小任务 → 直接优化提示词（但需要先定位）

### 优化后的提示词

```text
下面是问题描述：
登录接口（POST /api/auth/login）有时候返回 500 错误，不是每次都复现。

请先定位问题，不要直接修改代码。

排查步骤：
1. 阅读登录接口的完整代码，包括 Controller、Service、中间件。
2. 阅读错误处理和日志配置，找到 500 错误的日志记录。
3. 分析可能导致间歇性 500 的原因：
   - 数据库连接池耗尽？
   - 外部服务（如 Redis session）超时？
   - 并发竞态条件？
   - 未处理的 null/undefined？
4. 列出可能原因，按概率排序。
5. 标出最可能的根因及证据。

约束：
1. 不要直接改代码。
2. 先给出分析结论和最小修复方案。
3. 不要改变接口行为或返回格式。

需要的额外信息：
- 如果能找到相关错误日志，列出日志内容。
- 如果能判断出复现条件，说明复现路径。
```
