# 提示词优化方法论

把单个编程任务优化成 AI 编程工具能高质量执行的提示词。核心不是让 AI "更聪明"，而是让 AI 先获得足够上下文，在明确目标、边界、约束和验证方式后，小步、可控、可回滚地完成任务。

## 六条核心原则

### 1. 先读项目，再回答

默认要求 AI：
1. 先阅读当前项目结构
2. 找到与需求相关的文件、函数、接口、配置、测试
3. 明确当前实现方式和代码风格
4. 再输出方案或修改

如果当前环境无法访问项目文件，在提示词中明确要求：
> 先阅读当前项目结构，找到与该需求相关的代码文件，不要直接修改。先列出你找到的相关文件、函数、调用链和当前实现逻辑。

### 2. 具体优于模糊

补充：目标、范围、指标、位置、输入输出、边界条件。

❌ "帮我优化这个函数。"

✅ "先找到这个函数及其调用位置，分析当前性能瓶颈。该函数处理 10 万条数据时耗时约 30 秒，目标是降到 5 秒以内。可以考虑批处理、缓存、减少重复查询，但不要修改函数签名。"

### 3. 约束优于自由

常见约束清单：
- 不要改函数签名
- 不要引入新依赖
- 不要顺手重构无关代码
- 不要修改公共接口
- 不要改变已有返回格式
- 不要删除现有测试
- 不要改动数据库结构

### 4. 分步优于一次完成

标准流程：
1. 先分析现状和问题
2. 再给出方案选项
3. 等确认后再修改代码
4. 修改后说明改动点和验证方式

### 5. 示例优于描述

当要求统一格式时，直接给出期望的输入输出示例，不要用文字描述格式。

### 6. 参考现有代码优于从零开始

要求 AI 先找到项目中类似模块、接口、组件或测试，参考已有实现的风格。

> 参考 src/api/users.ts 的代码风格，实现 src/api/orders.ts。路由定义、错误处理、鉴权方式、返回格式都保持一致。

## 通用提示词骨架

```text
你是一个谨慎的资深软件工程师。请先阅读当前项目，不要直接修改代码。

任务：
[用户原始需求]

执行要求：
1. 先扫描项目结构，找到与该需求相关的文件、函数、组件、接口、配置、测试和调用链。
2. 先列出你找到的上下文信息，并说明你判断相关的原因。
3. 在没有确认根因或相关代码前，不要直接猜测，也不要直接改代码。
4. 如果需要修改代码，只改与该需求直接相关的最小范围。
5. 保持现有代码风格、命名习惯、错误处理方式、返回格式和测试风格。
6. 不要引入新依赖，除非先说明必要性并等待确认。
7. 不要顺手重构无关代码。
8. 修改后说明改了哪些文件、为什么改、如何验证。

现在请先执行第一步：阅读项目并列出相关上下文，不要修改代码。
```

## 优化时必须补充的问题

如果用户没有提供足够信息，在优化后的提示词中加入"需要 AI 主动查找"的要求：

1. 当前项目结构是什么？
2. 相关代码在哪些文件？
3. 有没有类似实现可以参考？
4. 输入输出是什么？
5. 是否有现有测试？
6. 是否允许改接口 / 数据库 / 依赖？
7. 需要保持哪些兼容性？
8. 修改完成后如何验证？

## 默认行为

| 用户要的 | 默认优化为 |
|---|---|
| 改代码 | 先读项目 → 找相关代码 → 分析上下文 → 给方案 → 等确认 → 再改 |
| 修 bug | 先读日志和代码 → 找证据 → 确认根因 → 给最小修复方案 → 再改 |
| 重构 | 先分析问题 → 给 2-3 个方案 → 说明风险 → 等确认 |
| 审查 | 限定文件和重点 → 按严重程度输出问题 → 给具体修改建议 |
