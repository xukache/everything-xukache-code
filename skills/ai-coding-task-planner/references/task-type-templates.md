# 任务类型模板

根据判断出的任务类型，选择对应模板生成提示词。

## A. 分析模式：先看后说

适合：理解代码、找问题、评估方案、梳理模块。

```text
先阅读当前项目中与 [需求/模块/问题] 相关的代码，不要直接修改。

重点分析：
1. 相关文件、函数、组件、接口和调用链。
2. 当前实现逻辑。
3. 可能存在的问题或风险。
4. 需要我确认的关键点。

输出要求：
- 只列出分析结果。
- 不要改代码。
- 不要给出大范围重构。
- 如果信息不足，说明还需要查看哪些文件或日志。
```

## B. 实现模式：明确需求

适合：新增功能、新接口、新组件、新脚本。

```text
请在当前项目中实现 [功能名称]。

开始前请先：
1. 阅读项目结构。
2. 找到类似功能或相邻模块。
3. 参考现有代码风格、目录结构、命名方式、错误处理和测试写法。
4. 列出你准备参考的文件和原因。

功能要求：
1. [具体要求 1]
2. [具体要求 2]
3. [具体要求 3]

约束：
1. 不要引入新依赖，除非先说明原因并等待确认。
2. 不要改变已有公共接口。
3. 不要修改无关文件。
4. 保持现有返回格式和错误处理风格。

完成后请输出：
1. 修改了哪些文件。
2. 每个文件为什么修改。
3. 如何运行或验证。
```

## C. 修复模式：给证据，少猜测

适合：Bug、异常、报错、线上问题。

```text
下面是错误描述 / 日志 / 复现步骤：

[粘贴错误信息]

请先定位问题，不要直接修改代码。

排查步骤：
1. 先阅读与错误相关的代码、配置、调用链和日志。
2. 根据日志和代码确认根因，不要只凭猜测。
3. 列出可能原因，并按概率排序。
4. 标出最可能的根因及证据。
5. 给出最小修复方案。

修改约束：
1. 只改必要代码。
2. 不要顺手重构。
3. 不要改变已有接口行为，除非这是 bug 根因。
4. 修复后补充或更新必要测试。

现在先完成根因分析，不要改代码。
```

## D. 审查模式：限定范围和重点

适合：代码审查、PR 审查、安全检查、性能检查。

```text
请审查 [文件/目录/PR]，先阅读相关上下文，不要修改代码。

重点关注：
1. 正确性：是否符合需求，是否有逻辑漏洞。
2. 边界情况：空值、异常输入、并发、失败重试等。
3. 性能：是否有重复查询、低效循环、内存问题。
4. 安全：鉴权、权限、输入校验、敏感信息泄露。
5. 可维护性：命名、结构、重复代码、测试覆盖。

输出要求：
- 按严重程度排序：高 / 中 / 低。
- 每个问题说明对应文件和位置。
- 给出原因、影响和建议修改方式。
- 不要输出泛泛而谈的建议。
```

## E. 重构模式：先方案，后动手

适合：模块重构、架构调整、代码整理。

```text
请重构 [模块/目录/功能]，但不要直接开始改代码。

第一步：
先阅读当前项目中与该模块相关的代码，包括入口、调用方、测试、配置和依赖关系。

第二步：
列出当前主要问题，例如：职责混乱、重复代码、耦合过高、测试困难、性能问题等。

第三步：
给出 2-3 个重构方案，每个方案说明：
1. 改动范围。
2. 优点。
3. 风险。
4. 是否需要迁移或兼容处理。
5. 推荐程度。

约束：
1. 不要直接修改代码。
2. 不要破坏现有 API。
3. 不要引入新依赖，除非必要。
4. 优先小步、安全、可回滚的方案。

现在只执行分析和方案设计，等我确认后再改代码。
```

## F. 性能优化模式：目标可量化

适合：慢查询、接口耗时、批处理、内存占用。

```text
请优化 [函数/接口/任务] 的性能。

已知现状：
- 当前性能：[例如处理 10 万条数据耗时 30 秒]
- 目标性能：[例如降到 5 秒以内]
- 限制条件：[例如不能改函数签名 / 不能改数据库结构]

请先阅读相关代码和调用链，不要直接修改。

分析要求：
1. 找出主要耗时点或复杂度问题。
2. 判断是否存在重复查询、重复计算、低效循环、无缓存、批量处理不足等问题。
3. 给出可选优化方案，并说明收益和风险。
4. 优先选择最小改动方案。

约束：
1. 不要改变外部行为。
2. 不要引入新依赖，除非先说明理由。
3. 不要为了性能牺牲明显的可读性。
4. 修改后说明如何压测或验证效果。
```

## G. 测试模式：补齐场景

适合：单元测试、集成测试、回归测试。

```text
请为 [功能/文件/函数] 补充测试。

开始前请先：
1. 阅读现有测试目录和测试风格。
2. 找到相似功能的测试写法。
3. 明确该功能的正常流程、异常流程和边界条件。

测试要求：
1. 覆盖正常输入。
2. 覆盖异常输入。
3. 覆盖边界情况。
4. 覆盖错误处理。
5. 如果涉及异步、缓存、权限或数据库，也要覆盖对应场景。

约束：
1. 不要改业务代码，除非发现代码无法测试且先说明原因。
2. 不要引入新的测试框架。
3. 保持现有测试命名和断言风格。

完成后说明如何运行测试。
```
