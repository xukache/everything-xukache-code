# AI 编程提示词优化 Skill

## 适用场景

当用户提供一段原始编程需求、报错描述、代码修改目标、重构想法、代码审查请求，或说“使用这个 Skill 优化下面的描述”时，使用本 Skill。

本 Skill 不是通用 Prompt Engineering 教程，而是专门用于 AI 编程工具场景，例如 Claude Code、Cursor、Copilot、ChatGPT 编程助手等。

目标是把用户的原始描述优化成：

- 更具体
- 有清晰约束
- 有执行步骤
- 有上下文补全要求
- 有禁止事项
- 更适合 AI 编程工具直接执行

---

## 核心工作原则

### 1. 先读项目，再回答

在优化或执行任何编程类需求前，必须优先补齐上下文。

默认行为：

1. 先阅读当前项目结构。
2. 找到与需求相关的目录、文件、函数、接口、配置、测试、日志或依赖。
3. 明确当前实现方式和代码风格。
4. 再输出优化后的提示词、分析结论或修改方案。

不要在不了解项目上下文的情况下直接猜测实现。

如果当前环境无法访问项目文件，需要在优化后的提示词中明确要求 AI 编程工具先读取项目，例如：

> 先阅读当前项目结构，并找到与该需求相关的代码文件，不要直接修改。先列出你找到的相关文件、函数、调用链和当前实现逻辑。

---

### 2. 具体优于模糊

原始描述如果过于笼统，需要补充目标、范围、指标、位置、输入输出、边界条件。

模糊表达：

> 帮我优化这个函数。

优化方向：

> 先找到这个函数及其调用位置，分析当前性能瓶颈。该函数处理 10 万条数据时耗时约 30 秒，目标是降到 5 秒以内。可以考虑批处理、缓存、减少重复查询或更换算法，但不要修改函数签名，也不要影响现有调用方。

---

### 3. 约束优于自由

AI 容易过度发挥，所以必须明确哪些事不能做。

常见约束包括：

- 不要改函数签名
- 不要引入新依赖
- 不要顺手重构无关代码
- 不要修改公共接口
- 不要改变已有返回格式
- 不要删除现有测试
- 不要改动数据库结构
- 不要影响兼容性

示例：

> 给 getUserById 增加缓存。使用内存缓存 Map，不要引入 Redis 或其他新依赖。TTL 为 5 分钟。只修改与 getUserById 直接相关的代码，不要改其他函数。

---

### 4. 分步优于一次完成

复杂任务必须拆成阶段，每一步完成后再进入下一步。

标准流程：

1. 先分析现状和问题。
2. 再给出方案选项。
3. 等确认后再修改代码。
4. 修改后说明改动点和验证方式。

示例：

> 重构认证模块，分三步进行。第一步：先阅读认证相关代码，分析当前问题和风险，只列出发现，不要改代码。第二步：基于发现给出 2-3 个重构方案，并说明优缺点。第三步：等我确认方案后再开始修改。现在只执行第一步。

---

### 5. 示例优于描述

当用户要求统一格式、风格、接口、错误处理、日志格式时，优先提供具体示例。

示例：

> 返回值统一为：
>
> ```json
> {
>   "code": 200,
>   "data": {},
>   "message": "success"
> }
> ```
>
> 错误时：
>
> ```json
> {
>   "code": 400,
>   "data": null,
>   "message": "参数 email 格式不正确"
> }
> ```

---

### 6. 参考现有代码优于从零开始

如果项目中已有类似模块、接口、组件、测试或工具函数，应要求 AI 先参考已有实现。

示例：

> 参考 src/api/users.ts 的代码风格，实现 src/api/orders.ts。路由定义、错误处理、鉴权方式、返回格式、日志写法都保持一致。不要自己创造新的项目风格。

## 使用方式

用户可以这样调用：

> 使用 AI 编程提示词优化 Skill，优化下面的需求：
> 原始描述：xxx

也可以简写：

> 用编程提示词 Skill 优化：xxx

输出时，应该先判断任务类型，再生成对应的优化版提示词。

## 输出格式

默认输出以下结构：

```markdown
## 判断的任务类型
[分析 / 实现 / 修复 / 审查 / 重构 / 测试 / 性能优化 / 文档 / 其他]

## 优化后的提示词
[可直接复制到 Claude Code、Cursor、Copilot 或其他 AI 编程工具中的完整提示词]

## 我补充的关键约束
1. ...
2. ...
3. ...

## 建议先让 AI 读取的上下文
1. 项目结构
2. 相关文件
3. 调用链
4. 测试文件
5. 日志 / 报错 / 配置
```

如果用户只想要可复制版本，可以只输出“优化后的提示词”。

## 通用提示词骨架

```text
你是一个谨慎的资深软件工程师。请先阅读当前项目，不要直接修改代码。

任务：
[用户原始需求]

执行要求：
1. 先扫描项目结构，找到与该需求相关的文件、函数、组件、接口、配置、测试和调用链。
2. 先列出你找到的上下文信息，并说明你判断相关的原因。
3. 在没有确认根因或相关代码前，不要直接猜测，也不要直接改代码。
4. 如果需要修改代码，只改与该需求直接相关的最小范围。
5. 保持现有代码风格、命名习惯、错误处理方式、返回格式和测试风格。
6. 不要引入新依赖，除非先说明必要性并等待确认。
7. 不要顺手重构无关代码。
8. 修改后说明改了哪些文件、为什么改、如何验证。

现在请先执行第一步：阅读项目并列出相关上下文，不要修改代码。
```

## 任务类型模板

### A. 分析模式：先看后说

适合：理解代码、找问题、评估方案、梳理模块。

```text
先阅读当前项目中与 [需求/模块/问题] 相关的代码，不要直接修改。

重点分析：
1. 相关文件、函数、组件、接口和调用链。
2. 当前实现逻辑。
3. 可能存在的问题或风险。
4. 需要我确认的关键点。

输出要求：
- 只列出分析结果。
- 不要改代码。
- 不要给出大范围重构。
- 如果信息不足，说明还需要查看哪些文件或日志。
```

---

### B. 实现模式：明确需求

适合：新增功能、新接口、新组件、新脚本。

```text
请在当前项目中实现 [功能名称]。

开始前请先：
1. 阅读项目结构。
2. 找到类似功能或相邻模块。
3. 参考现有代码风格、目录结构、命名方式、错误处理和测试写法。
4. 列出你准备参考的文件和原因。

功能要求：
1. [具体要求 1]
2. [具体要求 2]
3. [具体要求 3]

约束：
1. 不要引入新依赖，除非先说明原因并等待确认。
2. 不要改变已有公共接口。
3. 不要修改无关文件。
4. 保持现有返回格式和错误处理风格。

完成后请输出：
1. 修改了哪些文件。
2. 每个文件为什么修改。
3. 如何运行或验证。
```

---

### C. 修复模式：给证据，少猜测

适合：Bug、异常、报错、线上问题。

```text
下面是错误描述 / 日志 / 复现步骤：

[粘贴错误信息]

请先定位问题，不要直接修改代码。

排查步骤：
1. 先阅读与错误相关的代码、配置、调用链和日志。
2. 根据日志和代码确认根因，不要只凭猜测。
3. 列出可能原因，并按概率排序。
4. 标出最可能的根因及证据。
5. 给出最小修复方案。

修改约束：
1. 只改必要代码。
2. 不要顺手重构。
3. 不要改变已有接口行为，除非这是 bug 根因。
4. 修复后补充或更新必要测试。

现在先完成根因分析，不要改代码。
```

---

### D. 审查模式：限定范围和重点

适合：代码审查、PR 审查、安全检查、性能检查。

```text
请审查 [文件/目录/PR]，先阅读相关上下文，不要修改代码。

重点关注：
1. 正确性：是否符合需求，是否有逻辑漏洞。
2. 边界情况：空值、异常输入、并发、失败重试等。
3. 性能：是否有重复查询、低效循环、内存问题。
4. 安全：鉴权、权限、输入校验、敏感信息泄露。
5. 可维护性：命名、结构、重复代码、测试覆盖。

输出要求：
- 按严重程度排序：高 / 中 / 低。
- 每个问题说明对应文件和位置。
- 给出原因、影响和建议修改方式。
- 不要输出泛泛而谈的建议。
```

---

### E. 重构模式：先方案，后动手

适合：模块重构、架构调整、代码整理。

```text
请重构 [模块/目录/功能]，但不要直接开始改代码。

第一步：
先阅读当前项目中与该模块相关的代码，包括入口、调用方、测试、配置和依赖关系。

第二步：
列出当前主要问题，例如：职责混乱、重复代码、耦合过高、测试困难、性能问题等。

第三步：
给出 2-3 个重构方案，每个方案说明：
1. 改动范围。
2. 优点。
3. 风险。
4. 是否需要迁移或兼容处理。
5. 推荐程度。

约束：
1. 不要直接修改代码。
2. 不要破坏现有 API。
3. 不要引入新依赖，除非必要。
4. 优先小步、安全、可回滚的方案。

现在只执行分析和方案设计，等我确认后再改代码。
```

---

### F. 性能优化模式：目标可量化

适合：慢查询、接口耗时、批处理、内存占用。

```text
请优化 [函数/接口/任务] 的性能。

已知现状：
- 当前性能：[例如处理 10 万条数据耗时 30 秒]
- 目标性能：[例如降到 5 秒以内]
- 限制条件：[例如不能改函数签名 / 不能改数据库结构]

请先阅读相关代码和调用链，不要直接修改。

分析要求：
1. 找出主要耗时点或复杂度问题。
2. 判断是否存在重复查询、重复计算、低效循环、无缓存、批量处理不足等问题。
3. 给出可选优化方案，并说明收益和风险。
4. 优先选择最小改动方案。

约束：
1. 不要改变外部行为。
2. 不要引入新依赖，除非先说明理由。
3. 不要为了性能牺牲明显的可读性。
4. 修改后说明如何压测或验证效果。
```

---

### G. 测试模式：补齐场景

适合：单元测试、集成测试、回归测试。

```text
请为 [功能/文件/函数] 补充测试。

开始前请先：
1. 阅读现有测试目录和测试风格。
2. 找到相似功能的测试写法。
3. 明确该功能的正常流程、异常流程和边界条件。

测试要求：
1. 覆盖正常输入。
2. 覆盖异常输入。
3. 覆盖边界情况。
4. 覆盖错误处理。
5. 如果涉及异步、缓存、权限或数据库，也要覆盖对应场景。

约束：
1. 不要改业务代码，除非发现代码无法测试且先说明原因。
2. 不要引入新的测试框架。
3. 保持现有测试命名和断言风格。

完成后说明如何运行测试。
```

## 反模式处理规则

当用户原始描述出现以下问题时，必须主动修正：

| 原始说法 | 问题 | 优化方向 |
|---|---|---|
| 帮我写个网站 | 范围太大 | 拆成页面、接口、数据结构、交互等具体任务 |
| 优化一下 | 目标不明确 | 明确是性能、可读性、体积、稳定性还是体验 |
| 写最好的代码 | 标准不明确 | 改成可测试、可维护、符合项目风格、有错误处理 |
| 一次给很多需求 | AI 容易遗漏 | 拆成步骤，每步确认 |
| 修 bug 但不给日志 | AI 只能猜 | 要求提供错误日志、复现步骤、期望行为、实际行为 |
| 直接让 AI 改代码 | 可能误改 | 先读项目、找上下文、确认方案再改 |

---

## 优化时必须补充的问题

如果用户没有提供足够信息，优先在优化后的提示词中加入“需要 AI 主动查找”的要求，而不是直接追问用户。

应该补充：

1. 当前项目结构是什么？
2. 相关代码在哪些文件？
3. 有没有类似实现可以参考？
4. 这个功能的输入输出是什么？
5. 是否有现有测试？
6. 是否允许改接口 / 数据库 / 依赖？
7. 需要保持哪些兼容性？
8. 修改完成后如何验证？

## 最终可复制模板

```text
你是一个谨慎的资深软件工程师。请根据下面的原始需求工作，但在动手前必须先阅读当前项目并补齐上下文。

原始需求：
[在这里粘贴用户原始描述]

请按以下步骤执行：

第一步：项目上下文读取
1. 扫描项目结构。
2. 找到与该需求相关的文件、函数、组件、接口、配置、测试和调用链。
3. 找到可参考的已有实现或相似代码。
4. 总结当前实现逻辑。
5. 只输出你的发现，不要修改代码。

第二步：需求澄清与风险判断
1. 判断原始需求属于：分析 / 实现 / 修复 / 审查 / 重构 / 测试 / 性能优化 / 其他。
2. 列出需求中不明确的点。
3. 对每个不明确点，优先根据项目上下文做合理推断；不能推断的再标记为需要确认。
4. 列出可能影响现有功能的风险。

第三步：方案设计
1. 给出最小改动方案。
2. 说明会修改哪些文件。
3. 说明不会修改哪些内容。
4. 如果有多个方案，给出 2-3 个选项并推荐一个。

第四步：等待确认
在我确认之前，不要修改代码。

通用约束：
1. 不要引入新依赖，除非先说明必要性并等待确认。
2. 不要顺手重构无关代码。
3. 不要改变已有公共接口、返回格式、错误处理方式，除非这是明确需求。
4. 保持现有代码风格、命名方式、目录结构和测试风格。
5. 修改后必须说明改动点、影响范围和验证方式。
```

## 使用该 Skill 时的默认行为

当用户只给一句原始需求时，不要简单改写句子，而是要把它变成适合 AI 编程工具执行的完整任务说明。

当用户要“改代码”时，默认优化为：

> 先读项目 → 找相关代码 → 分析上下文 → 给方案 → 等确认 → 再改代码。

当用户提供报错时，默认优化为：

> 先读日志和代码 → 找证据 → 确认根因 → 给最小修复方案 → 再改代码。

当用户要求重构时，默认优化为：

> 先分析问题 → 给 2-3 个方案 → 说明风险 → 等确认。

当用户要求审查时，默认优化为：

> 限定文件和重点 → 按严重程度输出问题 → 给具体修改建议。

---

## 一句话版原则

> AI 编程提示词的核心不是让 AI “更聪明”，而是让 AI 先获得足够上下文，在明确目标、边界、约束和验证方式后，小步、可控、可回滚地完成任务。
