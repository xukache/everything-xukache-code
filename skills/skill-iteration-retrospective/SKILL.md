# Skill Iteration Retrospective

把一个已经存在、已经被使用过的 Skill，从“一次性提示词”维护成可持续迭代的工作资产。这个 Skill 不负责第一次创建 Skill，也不负责替用户选择要优化哪个 Skill；用户必须先指定目标 Skill。

使用本 Skill 时，先诊断，再改写。不要一看到失败输出就直接重写 `SKILL.md`。真正要迭代的通常不是措辞，而是触发条件、输入结构、判断规则、输出接口、审阅节点和失败回灌机制。

## 和 Skill Authoring 的关系

- 先用本 Skill 做复盘：判断为什么旧 Skill 失效、该改哪一层、需要新增哪些规则或模板。
- 形成新版 Skill 规格后，再用 `skill-authoring-workflow` 或 `skill-creator` 实现合规的文件修改。
- 如果用户只要求复盘或规划，不要修改目标 Skill 文件。

## 工作原则

- 迭代对象由用户指定，不做 Skill 选择或优先级排序。
- 失败样本优先于好评反馈；只记录“挺好用”很难改出有效规则。
- 把用户当作不了解 Skill 术语的人来引导。不要要求用户回答“触发条件、输出接口、主流程、必填输入”这类专业问题，要把它们翻译成具体、容易回答的小问题。
- 不追求信息完整，只追求足够做当前阶段判断。缺关键事实时暂停；缺非关键细节时可以继续，但必须标注“暂定”。
- 先定位失败层级，再决定是否修改 Skill。
- 对工作流类 Skill，必须检查“何时停止”和“哪些下游事情不该继续做”，避免把下一阶段建议误写成默认交付。
- 对交付物类 Skill，必须检查输出是否适合后续版本管理和协作流转；演示页面、临时稿和正式文档要分清。
- 每条新增规则都必须说明“为什么需要它”。
- 每轮迭代都留下版本说明和失败模式更新建议。
- 个人主用阶段保持轻量；团队评审可以作为可选升级，不作为默认流程。

## 快速启动

当用户要求迭代某个 Skill 时，先确认三件事：

```text
目标 Skill：
本轮迭代动机：
可用失败样本：
本轮要防止的偏差：例如职责外扩、提前生成、缺少 Markdown/PRD/交接文档、没有停在评审节点
```

用户提供的材料可能不是标准问题描述，而是一整段和 Skill 的对话记录、零散抱怨、截图转写、人工修改前后的片段，或一句“这次跑偏了”。先从材料中抽取可判断事实，再标注缺口并追问。不要要求用户先把材料整理成标准格式。

如果缺少失败样本，按 `references/failure-sample-template.md` 引导用户补齐。不要直接基于模糊感受改写 Skill。

## 阶段门槛与判断依据

每进入下一阶段前，必须显式输出阶段门槛判断，禁止只在内部确认。用户需要能看到为什么可以继续、哪里只是暂定、还缺什么信息。

```text
当前阶段：
信息等级：足够 / 暂定足够 / 不足 / 无法判断
判断依据：
信息缺口：
下一步动作：继续 / 暂定继续 / 追问 / 停止
```

信息等级定义：

- **足够**：有明确事实支撑，可以进入下一步并给出结论。
- **暂定足够**：信息不完整，但足以给出暂定判断；输出中必须标注哪些内容待确认。
- **不足**：缺少关键事实，继续会导致误判；先用小白友好问题追问。
- **无法判断**：缺少目标 Skill 或具体失败事件；不能进入复盘。

### 门槛 1：是否能开始复盘

可以开始的最低标准：

- 能知道用户想迭代哪个 Skill，或能从上下文推断出唯一目标 Skill。
- 能知道用户大概为什么不满意，例如“跑偏了”“返工了”“没问清楚”“输出没人用”。
- 有一段可分析材料：对话记录、原始输入、输出片段、用户抱怨、人工修改结果中的任意一种。

不能开始时这样问：

```text
我现在还不知道要复盘哪个 Skill。你只要告诉我名字，或者把相关文件/对话贴过来就行。
```

### 门槛 2：是否能整理失败样本

可以整理的最低标准：

- 能看出用户原本想完成什么。
- 能看到 AI 或 Skill 做了什么，哪怕只是用户转述。
- 能看到用户觉得哪里不对，或者最后哪里返工。

判断依据：

- 缺少“AI 做了什么”：只能做用户诉求整理，不能做失败归因。
- 缺少“哪里不对”：只能整理事实，不能判断失败层级。

小白友好追问：

```text
我现在能看出你想做什么，但还看不出 AI 到底哪里做错了。
你按自己的话补一句就行：它最后给你的东西，哪里让你觉得不对？
```

### 门槛 3：是否能进入失败归因

可以归因的最低标准：

- 能比较“用户原本想要的结果”和“Skill 实际产出的结果”。
- 能判断偏差更像发生在：太早开始、信息没问够、判断规则没写清、输出没人接得住。
- 若目标 Skill 是多阶段工作流，能判断偏差是否发生在“继续下一步”建议、最终交付确认、职责边界或停止条件上。
- 至少有一个可引用的事实支撑归因。

归因清晰度：

- **足够**：有原始输入、关键输出、用户反馈或人工修正，可明确主因。
- **暂定足够**：材料来自用户转述，但能看出明显偏差，可先给暂定归因。
- **不足**：只知道“不满意”，不知道原始输出或返工点，需要追问。
- **无法判断**：没有目标 Skill 或具体失败事件，不能归因。

小白友好追问：

```text
我现在还不能判断是“AI 太早开始做了”，还是“它没问够问题”。
你回忆一下：它是一上来就开始产出，还是问了问题但问偏了？
```

### 门槛 4：是否能生成新版 Skill 规格

可以生成规格的最低标准：

- 已经有一个主归因，或明确标注多个问题叠加。
- 能说清楚下次要避免什么失败。
- 能提出至少一条可执行规则，例如“缺少某类信息时先追问”或“不要直接生成某类输出”。
- 若存在职责外扩，能写出“到哪一步必须停止/确认”和“哪些产物只能作为建议、不能默认生成”。
- 能说明这条规则为什么需要。

不能生成规格时，只输出诊断和缺口，不输出改写建议。

小白友好追问：

```text
我已经知道这次哪里跑偏了，但还不知道你希望下次 AI 怎么停下来。
下次它正式开始写东西前，你希望它先问清楚哪几件事？
想到几条写几条就行。
```

### 门槛 5：是否能进入实际修改

可以修改目标 Skill 的最低标准：

- 用户已经看过本轮诊断和新版 Skill 规格，并再次明确要求“按这个规格修改文件”。
- 新版规格已经列出要改的触发条件、输入要求、判断规则或输出格式。
- 能区分“本轮要改”和“本轮不改”。
- 目标 Skill 路径明确且可访问。

硬性停止规则：

- 用户第一次说“迭代、优化、改进某个 Skill”，只能视为进入复盘流程，不等于允许编辑文件。
- 在输出诊断、失败归因、新版规格和版本说明草稿之前，禁止调用 `apply_patch`、写文件、移动文件或生成新 reference。
- 只有用户在看完规格后再次明确说“按这个规格修改文件”“开始实现这个修改”“可以落地到文件”，才允许进入实际修改。
- 如果用户只是在复盘，不进入修改。输出规格、版本说明草稿和失败模式库建议即可。

## 工作流

### 阶段 1：确认迭代目标

用户必须指定要迭代的 Skill，并说明为什么现在要改：

- 最近哪次使用出了问题。
- 哪类输出不符合预期。
- 哪个环节返工最多。
- 是修复失败、补充能力、收敛输出格式，还是降低误触发。
- 是否出现了边界外扩：例如把产品需求梳理扩成技术方案、架构设计、排期承诺或其他非本 Skill 职责。

如果目标 Skill 路径可访问，读取目标 Skill 的 `SKILL.md` 和直接引用的 reference 文件。只读取与本轮问题相关的内容，避免把整个技能库塞进上下文。

读取目标 Skill 后，先摘出三件事：

- 目标 Skill 自己声明的用途和交付物。
- 目标 Skill 自己声明的“不做 / 后置 / 暂停确认 / 停止条件”。
- 目标 Skill 对下游交接的要求，例如 HTML 演示、Markdown 文档、PRD、流程图、开发交接或版本化索引。

输出一段迭代目标摘要：

```text
目标 Skill：
当前用途：
本轮问题：
期望改善：
本轮不处理：
```

### 阶段 2：建立或更新 Skill 迭代卡

使用 `references/iteration-card-template.md` 整理目标 Skill 的维护信息。迭代卡回答：

- 什么时候应该触发这个 Skill。
- 什么时候不应该触发这个 Skill。
- 没有哪些输入时不允许继续。
- 输出最终给谁用。
- 什么样的输出才算能进入下一环节。
- 哪些输出只是建议，不应被默认实现。
- 什么时候应该停止并等待用户确认。
- 本轮为什么要改。

如果目标 Skill 已经有迭代卡，先更新卡片；如果没有，先生成草案，不要把草案当事实。

### 阶段 3：收集失败样本

用户可能直接贴出原始对话记录。先把对话记录拆成结构化失败样本：

- 用户最初想让 Skill 完成什么。
- 用户实际给了哪些输入、上下文、约束和补充说明。
- Skill 在哪些节点做了判断、追问或直接生成。
- Skill 的关键输出是什么。
- Skill 在“下一步”建议里是否扩大了职责边界。
- Skill 最终产物是否缺少版本管理或下游交接所需格式。
- 用户在对话中表达了哪些不满、修正、否定或补充。
- 最后人工修正方向是什么。

如果对话记录里没有明确说出“为什么失败”，不要替用户武断下结论。先输出“可判断事实 / 推测 / 待确认信息”三栏，然后只追问会影响归因判断的问题。

每个失败样本都按五类信息整理：

- 原始任务：当时希望 AI 完成什么。
- 原始输入：当时提供了哪些文档、背景、约束和提示词。
- 原始输出：AI 实际产出了什么。
- 真实偏差：为什么没进入工作流，或进入后为什么出问题。
- 人工修正：最后用户、开发、UX、业务方或管理者怎么改。

如果失败样本来自多轮“继续下一步”，还要额外抽取：

- 完成线：目标 Skill 按自身流程本应在哪个阶段停下来。
- 越界动作：AI 建议或生成了哪些职责外产物。
- 缺失交付：用户后来要求补出的正式文档、可 diff 文档、索引或归档说明。
- 收敛提醒：用户用哪些话要求“不要扩大职责边界”或“回到真实需求”。

如果样本信息不足，先追问缺失项。追问应尽量少而关键，优先补齐能区分“触发时机错误、输入缺失、判断规则缺失、输出接口不匹配”的信息。不要把“输出不满意”直接当成可执行诊断。

追问时使用用户能直接回答的说法：

| 不要这样问 | 改成这样问 |
| --- | --- |
| 业务方最终认可的主流程是什么？ | 后来业务方说“正确方向”应该怎么做？你可以按 1、2、3 写，不用写专业流程图。 |
| 新版 Skill 在什么条件下才允许开始写 HTML？ | 下次 AI 开始写页面前，你希望它先问清楚哪几件事？比如：给谁用、要解决什么问题、现在怎么做、哪些先不做。 |
| 缺少哪些必填输入？ | 这次如果 AI 一开始多问你几个问题，问哪些问题就能避免返工？ |
| 输出接口哪里不匹配？ | 这份结果最后是谁用不起来？是你、业务方、开发、测试，还是设计？他们卡在哪里？ |
| 触发时机哪里错了？ | AI 是不是太早开始做某件事了？如果是，它应该先停下来确认什么？ |

追问示例：

```text
我先不问很专业的问题。你按自己的话补两点就行：
1. 后来你们觉得“正确方向”应该是什么？可以简单写成第一步、第二步、第三步。
2. 下次 AI 开始正式产出前，你希望它先问清楚哪几件事？不用完整，想到什么写什么。
```

信息充分性最低标准：

```text
1. 能看出目标 Skill 是哪个。
2. 能看出用户原本想完成什么。
3. 能看到 Skill 的实际输出或关键行为。
4. 能知道用户认为哪里不对，或下游在哪里返工。
```

若缺少第 1 项或第 2 项，必须先追问；若缺少第 3 项或第 4 项，可以先做初步整理，但归因必须标记为暂定。

### 阶段 4：失败归因

先把失败样本归因到以下层级，再决定修改位置：

| 归因类型 | 判断方式 | 常见修正方向 |
| --- | --- | --- |
| 触发时机错误 | Skill 在错误阶段被调用 | 调整 description、禁用场景、触发前提 |
| 输入信息缺失 | 上下文缺角色、场景、指标、约束或历史决策 | 增加必填输入、暂停追问、输入模板 |
| 判断规则缺失 | 关键权衡靠默认常识猜 | 新增显性判断规则、优先级或取舍准则 |
| 输出接口不匹配 | 内容不差但下游接不住 | 调整输出对象、格式、粒度和完成标准 |
| 职责边界漂移 | Skill 已完成主线后继续扩展到下游专业领域 | 增加完成线、禁用产物、最终确认后的收敛动作 |
| 多个问题叠加 | 同时存在多个失败层级 | 先修最早导致偏差的层级 |

输出固定诊断格式：

```text
1. 问题归因：
2. 缺失信息清单：
3. 本应提前显性化的判断规则：
4. 建议新增或修改的输入字段：
5. 建议新增或修改的审阅节点：
6. 建议新增或修改的停止条件：
7. 不建议修改的部分：
```

### 阶段 5：生成新版 Skill 规格

只有完成失败归因后，才输出新版 Skill 规格。使用这个结构：

```text
1. Skill 目标
2. 适用场景与禁用场景
3. 触发前提
4. 必填输入字段
5. 关键判断规则
6. 输出对象与输出格式
7. 停止条件与职责边界
8. 审阅与升级机制
9. 常见失败模式与防错提醒
```

每条新增规则必须附一句原因：

```text
规则：
原因：
```

规格说明不是 `SKILL.md` 正文。用户确认规格后，才进入实现或改写阶段。

### 阶段 6：轻量评审与试跑建议

个人主用阶段默认给出最小试跑方案：

- 用一个旧失败样本回放，检查新版规格能否避免同类问题。
- 用一个新任务样本试跑，检查新版规格是否过重。
- 检查输出能否直接进入下一环节，而不是还要大量人工翻译。
- 检查输入不足时，Skill 是否会停下来追问，而不是硬生成。
- 检查主线完成后，Skill 是否会进入确认、归档或交接，而不是继续生成职责外的技术方案、排期或实现细节。
- 检查正式交付物是否有可版本管理的源文件；如果只有 HTML 或截图，必须说明是否需要 Markdown、Mermaid 源码或其他可 diff 格式。

如果用户说明这是团队共用 Skill，再补充开发、测试、UX 或业务方的轻量审阅问题。

### 阶段 7：版本说明与失败模式库

每轮迭代结束时，输出：

- 版本说明草稿：这一版改了什么、为什么改、解决哪类失败。
- 失败模式库更新建议：哪些场景容易误触发、哪些输入最常缺、哪些规则最容易被误解。
- 若本轮发现职责边界漂移，把“越界触发语、越界产物、正确停止动作”写入失败模式库。

使用 `references/version-note-template.md` 组织版本说明。失败模式要写成可复用经验，不要只记录一次性抱怨。

## 输出清单

本 Skill 的默认输出是复盘与规格，不是直接改文件：

- 失败归因报告。
- 缺失输入清单。
- 应显性化的判断规则。
- 建议新增或修改的输入字段。
- 建议新增或修改的审阅节点。
- 建议新增或修改的停止条件与禁用产物。
- 新版 Skill 规格说明。
- 旧失败样本回放结果。
- 版本说明草稿。
- 失败模式库更新建议。

默认只复盘，不修改文件。即使用户说“帮我迭代优化这个 Skill”，也只输出失败归因、缺失输入、应显性化规则、新版规格、版本说明草稿和失败模式库更新建议。必须在用户看完规格后再次明确要求“按这个规格修改文件”，才编辑目标 Skill 文件。

## 质量检查

交付前检查：

- 每一步是否有判断依据，而不是凭感觉推进。
- 阶段门槛是否显式输出，而不是只在内部确认。
- 是否把用户第一次提出“迭代优化”误判成允许直接改文件。
- 如果信息等级是“暂定足够”，是否明确标注了待确认内容。
- 是否使用了用户指定的目标 Skill，而不是重新选择对象。
- 是否至少基于一个失败样本或明确迭代动机。
- 如果用户提供的是原始对话记录，是否先完成事实抽取和信息缺口标注。
- 是否先诊断再提出改写方案。
- 是否区分触发、输入、判断规则和输出接口问题。
- 是否检查目标 Skill 的职责边界、停止条件和禁用产物。
- 是否检查最终产物是否适合版本管理和下游交接。
- 是否说明每条新增规则的原因。
- 是否留下版本说明和失败模式更新建议。
- 是否避免把简单措辞偏好包装成工作流规则。
