# 失败样本模板

使用这个模板记录一次失败或不符合预期的 Skill 调用。一个有价值的失败样本，必须能说明 Skill 使用前、使用中、使用后分别发生了什么。

用户可能不会提供标准描述，而是直接贴出一段和 Skill 的对话记录。先解析对话，再整理失败样本；不要要求用户先按模板重写。

## 对话记录解析

```text
原始对话记录：
- 

可判断事实：
- 目标 Skill：
- 用户最初目标：
- 用户提供的输入：
- Skill 的关键行为：
- Skill 的关键输出：
- Skill 的下一步建议：
- Skill 声明的职责边界：
- 用户表达的不满或修正：
- 后续人工处理：

合理推测：
- 

待确认信息：
- 

下一步追问：
1. 
2. 
3. 
```

追问原则：

- 只问会影响失败归因的问题。
- 优先补齐目标 Skill、原始任务、实际输出、真实偏差。
- 对无法从对话记录确认的信息，标记为“待确认”，不要当成事实。
- 如果材料足够做初步归因，但不足以给出修改方案，先输出初步诊断，再要求用户补充关键缺口。
- 不要用“触发条件、输出接口、主流程、必填输入、审阅节点”这类术语追问用户；要翻译成“AI 是不是太早开始做了什么”“下次正式产出前要先问清哪几件事”“最后是谁用不起来”。

## 小白友好追问示例

```text
我先不问专业术语，你按自己的话补充就行：

1. 后来你们觉得正确方向应该是什么？
   可以写成“先做 A，再做 B，最后做 C”，不用画流程图。

2. 这次如果 AI 一开始多问你几个问题，问哪些问题就能避免返工？
   比如：给谁用、要解决什么问题、现在怎么做、哪些先不做、最后给谁看。

3. 这份输出最后是谁用不起来？
   是你自己、业务方、开发、测试、设计，还是其他人？他们具体卡在哪里？
```

追问改写对照：

```text
专业问法：业务方最终认可的主流程是什么？
用户友好问法：后来业务方说正确方向应该怎么做？按 1、2、3 写就行。

专业问法：新版 Skill 在什么条件下才允许开始生成？
用户友好问法：下次 AI 开始正式写东西前，你希望它先问清楚哪几件事？

专业问法：输出接口哪里不匹配？
用户友好问法：这份结果最后谁接不住？他看完以后还得补什么、改什么？
```

## 失败样本

```text
目标 Skill：
日期或项目：
原始任务：

原始输入：
- 文档：
- 背景：
- 约束：
- 提示词：

原始输出：
- 

真实偏差：
- 为什么这份输出没能进入工作流？
- 如果进入了工作流，它在哪个环节造成了返工？
- 是否发生职责边界漂移？如果是，越界到了什么下游领域？
- 是否缺少正式交付或版本管理格式？

人工修正：
- 用户最后改了什么？
- 下游评审人最后改了什么？
- 最终被接受的版本是什么？

正确停止动作：
- 当时 Skill 应该在哪一步停下来？
- 应该提醒用户确认什么？
- 哪些内容应该只列为后续建议，而不是默认生成？

影响：
- 损失时间：
- 造成返工：
- 延误决策：
- 影响对象：
```

## 信息充分性检查

```text
当前阶段：
信息等级：足够 / 暂定足够 / 不足 / 无法判断

判断依据：
- 是否能确认目标 Skill：
- 是否能确认原始任务：
- 是否能看到实际输出或关键行为：
- 是否能确认真实偏差或返工点：
- 是否至少有一个事实支撑归因：
- 如果是多阶段工作流，是否能确认正确停止点：
- 如果涉及交付物，是否能确认下游需要的正式格式：

信息缺口：
- 

下一步动作：继续 / 暂定继续 / 追问 / 停止
```

## 信息等级说明

```text
足够：
- 有原始输入、关键输出、用户反馈或人工修正。
- 可以明确进入失败归因或新版规格生成。

暂定足够：
- 材料主要来自用户转述，但能看出明显偏差。
- 可以继续，但输出必须标注“暂定”和“待确认”。

不足：
- 只知道用户不满意，但不知道 AI 做了什么或哪里返工。
- 需要先追问，不能生成新版规格。

无法判断：
- 目标 Skill 不明确，或没有具体失败事件。
- 不能复盘，必须先让用户补充最基础信息。
```

## 阶段门槛速查

```text
能开始复盘：
- 知道要复盘哪个 Skill。
- 知道用户大概为什么不满意。
- 有对话记录、输出片段、抱怨或人工修正中的任意一种材料。

能整理失败样本：
- 看得出用户原本想做什么。
- 看得到 AI/Skill 做了什么。
- 看得到用户觉得哪里不对，或最后哪里返工。

能进入失败归因：
- 能比较“用户想要的”和“Skill 实际给的”。
- 至少有一个事实支撑偏差判断。

能生成新版规格：
- 已经有主归因。
- 能说清楚下次要避免什么。
- 至少能提出一条可执行规则，并说明原因。

能进入实际修改：
- 用户已经看过诊断和新版规格，并再次明确要求按该规格改文件。
- 新版规格已确认。
- 本轮要改和不改的边界清楚。
- 目标 Skill 路径可访问。
```

## 归因分类

在提出修复方案前，先选择一个主要归因：

```text
1. 触发时机错误
2. 输入结构缺失
3. 判断规则缺失
4. 输出接口不匹配
5. 职责边界漂移
6. 多个问题叠加
```

## 诊断输出

```text
1. 问题归因：
2. 缺失信息：
3. 本应提前显性化的判断规则：
4. 建议新增或修改的输入字段：
5. 建议新增或修改的审阅节点：
6. 建议新增或修改的停止条件：
7. 不应该修改的部分：
```

## 反模式

- 不要在缺少原始输入和原始输出时，仅凭“我感觉不好”做诊断。
- 不要在识别失败层级前，直接重写目标 Skill。
- 不要把一次性的风格偏好当成工作流规则，除非它造成了真实返工。
- 不要新增无法关联到失败样本或明确迭代目标的规则。
- 不要把“下一步可以考虑”误写成“本 Skill 默认要交付”的内容。
- 不要在用户已经要求收敛时继续扩展到下游专业领域。
- 不要把用户第一次说“迭代优化这个 Skill”理解为允许直接改文件；第一次只做复盘和规格，等用户二次确认后再实现。
