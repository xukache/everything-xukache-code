# 提示词模式

根据任务类型选择提示词结构。不要机械套模板，优先保留任务真正需要的约束、示例和输出格式。

## 通用骨架

```text
你是[角色/能力边界]。

<task>
[明确任务目标和成功标准]
</task>

<input>
[用户输入或占位符]
</input>

<rules>
1. [必须遵守的约束]
2. [不能编造/不能越权/不能修改的事项]
3. [信息不足或失败时的处理方式]
</rules>

<output_format>
[自然语言/Markdown/JSON/schema/字段说明]
</output_format>

<self_check>
最终输出前检查：
1. 是否满足输出格式。
2. 是否所有结论都有依据。
3. 是否按失败规则处理缺失信息。
</self_check>
```

## 抽取型

适合简历、票据、病历、工单、合同、网页内容等字段抽取。

关键规则：
- 字段缺失返回 `null`。
- 不允许根据常识补全。
- 多值字段使用数组。
- 输出严格合法 JSON。

```text
请从 <input> 中抽取指定字段，并只输出合法 JSON。

字段定义：
- name: 人名；原文未出现则为 null
- issue_type: 投诉类型；只能取 ["物流", "质量", "售后", "其他"]
- evidence: 支持该字段的原文短句

规则：
1. 只能依据输入文本抽取，不得编造。
2. 字段缺失时返回 null。
3. 输出必须符合 JSON，不要添加解释。
```

## 证据问答型

适合 RAG、知识库问答、文档问答、政策问答。

关键规则：
- 只能依据给定证据回答。
- 证据不足返回 `cannot_answer`。
- 输出引用 `evidence_ids` 或来源列表。

```text
请只依据 <evidence> 回答 <question>。

规则：
1. 如果证据不能支持答案，返回 cannot_answer。
2. 不要使用外部知识补充。
3. 每个结论都必须关联 evidence_ids。

输出格式：
{
  "answer": "string | cannot_answer",
  "evidence_ids": ["string"],
  "reason": "string"
}
```

## 分类型

适合意图识别、标签分类、内容审核、情绪识别。

关键规则：
- 给清楚 label 定义。
- 处理标签重叠和无法判断。
- 示例覆盖边界。

```text
请将输入文本分类到一个最合适的标签。

标签：
- refund: 用户要求退款或退货
- complaint: 用户表达不满但未要求退款
- consult: 用户询问信息
- other: 不属于以上类别

规则：
1. 若同时出现退款和投诉，优先 refund。
2. 无法判断时输出 other。

输出 JSON：
{"label":"refund|complaint|consult|other","confidence":0-1,"reason":"简短理由"}
```

## 工具调用型

适合 Agent、函数调用、自动化工作流。

关键规则：
- 明确何时调用工具。
- 明确工具失败怎么办。
- 禁止未调用工具时声称已完成。
- 工具返回后再综合回答。

```text
你可以使用工具完成任务。

工具边界：
- search_docs: 只用于检索内部文档。
- create_ticket: 只在用户明确要求创建工单时调用。

规则：
1. 需要最新或内部信息时必须先调用 search_docs。
2. 工具失败时输出 error_reason，不要假装成功。
3. 未调用 create_ticket 时，不得说工单已创建。
4. 最终回答必须说明依据的工具结果。
```

## 评审打分型

适合 LLM-as-a-Judge、内容审核、简历评分、方案评估。

关键规则：
- rubric 必须可观察。
- 先列观察，再给分。
- 分数等级定义清楚。
- 不允许引入 rubric 外标准。

```text
请根据 rubric 评审输入内容。

评分维度：
1. 准确性：0-5，事实是否正确。
2. 完整性：0-5，是否覆盖要求。
3. 可执行性：0-5，是否有明确下一步。

规则：
1. 先列 observation，再给 score。
2. 只能依据 rubric 评分。
3. 不确定时降低置信度并说明原因。
```

## Agent 工作流型

适合多轮任务、长任务、文件操作、工具链任务。

关键规则：
- 定义阶段和检查点。
- 定义状态记录和恢复方式。
- 定义何时停止、何时询问用户。
- 定义完成证据。

```text
按阶段执行任务：
1. 收集上下文：列出已读材料和缺口。
2. 制定计划：给出可验证步骤。
3. 执行：每次只改一个小范围。
4. 验证：运行指定检查并记录结果。
5. 交付：说明改动、证据和剩余风险。

停止条件：
- 缺少权限、关键输入或验证无法运行时，说明阻塞原因。
- 完成所有验收标准并给出验证证据时停止。
```
