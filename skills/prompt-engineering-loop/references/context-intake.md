# 上下文收集

用于把用户的一句话意图或粗糙 prompt 补齐到可以稳定生成提示词的程度。

## 快速引导语

```text
请把你想优化的意图或现有提示词发给我。最好同时补充：
1. 这个 prompt 用在什么场景、给谁用。
2. 模型会收到什么输入，最好给 1-3 个真实样本。
3. 你希望输出什么格式，是否需要 JSON/schema/表格。
4. 哪些内容不允许编造，信息不足时应该怎么返回。
5. 你现在遇到的失败样本或不满意之处。
6. 你希望用什么指标判断优化后更好。
```

## 最小问题集

当用户上下文不足时，优先问这些问题：

1. 这个提示词的最终任务是什么？请用一句可验收的话描述。
2. 模型输入来自哪里？用户自由输入、文档证据、数据库、工具结果还是固定表单？
3. 期望输出给人读还是给程序解析？如果给程序解析，需要什么字段？
4. 信息缺失、证据不足或请求越权时，模型应该返回什么？
5. 有没有 1 个理想输出样本和 1 个失败样本？

## 完整上下文表

| 信息 | 说明 | 示例 |
|---|---|---|
| 任务目标 | 模型要完成的动作和成功标准 | 从客服记录中抽取投诉原因并分类 |
| 用户/受众 | 最终读者或系统调用方 | 运营人员、后端服务、审核系统 |
| 使用位置 | 聊天窗口、API、Agent 节点、批处理 | RAG 问答接口 |
| 输入内容 | 输入字段、来源、格式、长度 | query + top_k 文档片段 |
| 输出格式 | 自然语言、Markdown、JSON、函数参数 | JSON 数组，每项含 label/confidence |
| 证据边界 | 能依据什么回答，不能依据什么 | 只能依据 provided_context |
| 失败处理 | 缺字段、无证据、工具失败、越权 | 返回 cannot_answer 和 reason |
| 风格要求 | 语气、长度、语言、术语 | 简洁中文，不超过 120 字 |
| 工具能力 | 可调用工具、参数、限制 | search_docs(query, top_k) |
| 评测指标 | 怎么判断更好 | 格式合法率、幻觉率、召回率 |
| 约束 | 成本、延迟、模型、上下文长度 | 使用小模型，单次 4k token 内 |

## 上下文不足时的输出规则

如果缺关键信息：

- 不要直接编一个看似完整的 prompt。
- 先列出缺失信息对效果的影响。
- 问最少必要问题。
- 若用户要求先给初版，标注假设和风险。

## 输入边界建议

优先使用明确分隔：

```text
<rules>
...
</rules>

<input>
...
</input>

<examples>
...
</examples>

<output_format>
...
</output_format>
```

也可以使用 Markdown heading 或 JSON 包裹。关键是让模型区分规则、数据、示例和输出要求。
