# 工艺准则(贯穿全程)

> 这份文件描述**怎么做**(怎样和用户协作),独立于"做什么"(各阶段产物)。每个阶段、每个角色、每次对话都要遵守。

## 1. 一次只抛一项

把每个决策拆到**最小可拍板单位**(一页、一项功能、一条流程节点、一个交互),然后一次只抛一项给用户拍板;确认一项落盘一项,再进入下一项。

- **为什么**:用户一次只能做一个判断;一次塞 5 个决定会被略读、被默认全选,事后才发现没真正被确认。
- **怎么落地**:不要把整页设计/整章 PRD 一次性丢给用户说"看看可以吗";要拆成"P1 这一页给谁用?(我建议……)"这种粒度。

## 2. 决策三件套(推荐 + 理由 + 取舍)

每个抛给用户的选择都要带:
- **推荐方向**:你建议怎么做。
- **为什么这么定**:基于哪个用户场景/约束/经验。
- **如果走另一种**:对应的代价或损失是什么。

- **为什么**:用户不需要被动选 A/B/C;用户需要的是「让我看到你的判断逻辑,我来纠偏」。
- **怎么落地**:禁止抛裸选择题"你要 1 还是 2?";禁止只给方案不给理由。

## 3. 守边界(MVP 暂不做项要标清)

每个阶段都明确「这一版做」「二期做」「不做」三档,用户提出超范围需求时**不直接接住**,先回到 MVP 边界确认。

- **为什么**:产品最大杀手是范围蔓延;蔓延通常发生在中后期"既然都做了顺手……"的微小扩张里。
- **怎么落地**:任何"加个小功能"都要标 P0/P1/P2 或 MVP/二期/不做。

## 4. 重大变革协议

用户提出的**方向性改动**(改流程主骨架、改主交互、改产品形态)走以下五步,**禁止**直接顺手改:

1. **验证洞察**:确认用户提的问题确实存在(不是误解、不是孤立 case)。
2. **梳理连锁影响**:这个改动会牵动哪些已确认的页/流程/功能/数据。
3. **确认范围**:把所有连锁影响列给用户,确认要不要全改。
4. **全文一致传播**:已确认的所有上下游文档都要更新,不留旧版本。
5. **一致性检查**:跑完整 sweep,确保没有 A 处改了 B 处忘改。

- **为什么**:大改不做这五步,产物会"半新半旧",后续基于矛盾文档做决策会越走越偏。
- **怎么落地**:用户说"我想换种方式做"时,先停下手上的实现,走完上面五步再继续。

## 5. 一致性检查(每次大改后必做)

任何重大变革或多文档改动后,跑完整 sweep:
- 上游事实(产品定位、目标用户、平台、范围)有没有被本次改动撼动? 有就回写。
- 下游产物(handoff、原型、任务)是否需要重排? 需要就同步。
- 同一术语/编号/页面名在所有文档里是否一致?

- **为什么**:多文档协作的项目,真理只能有一个版本;矛盾的文档比缺失的文档危害更大。
- **怎么落地**:不要求固定表格格式,但要确认这件事被做了;review 阶段会兜底检查。

## 6. 可追溯(决策落到文字)

每个非显然的决策就地记一句**为什么**(基于哪条用户原话、哪个约束、哪个权衡),不要只留结果。

- **为什么**:三周后任何人(包括你自己)看着结果都会问「为什么是这样」;没有 why 的决策会被反复重新讨论。
- **怎么落地**:在产物文档里就地用斜体或括号备注写一句依据,例如*依据:用户在 init 阶段确认每天打开 < 3 次,所以入口收纳到二级*。
