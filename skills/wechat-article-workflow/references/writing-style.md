# 写作风格和改稿自检

本文件只管语言、段落和改稿判断。长期作者人设的唯一来源是 `author-persona.md`，不要在这里另立人设规则。

## 基本语气

- 素材支持时，使用第一人称经验。
- 段落以短段和中等长度段落为主。
- 使用朴素的技术表达。
- 读起来要像一个人真的打开过文件、跑过工具、做过选择、纠正过 AI。
- 通过实际过程解释原则，不要把原则写成脱离场景的口号。

## 句子规则

- 一句话只说一件事。长句如果塞了多个判断，拆开。
- 先具体，再抽象。抽象词只有在具体材料已经充分时才用于收束。
- 重要判断可以单独成段。
- 不要为了显得高级而牺牲可读性。
- 信息已经自明时，直接说结论和动作，不要补一串“为什么它重要”“它适合什么”“它解决了什么”的硬解释。

## 具体性

抽象表述必须尽量换成读者能看见的说法：

- “显著提升效率” -> 写清原来多久、现在多久。
- “优化体验” -> 写清少点了哪一步、少等了什么。
- “沉淀方法论” -> 写清沉淀到哪个文件、下次怎么复用。
- “形成闭环” -> 写清输入、产物、检查点和下一次如何接上。

无法具体化时，不要硬写成结论。保留占位，说明需要补什么证据。

不要把所有具体信息都展开解释。具体性是为了让读者看清楚，不是把每个名词、每个选择和每个背景都讲一遍。读者不关心、不会影响理解、也不支撑主线的细节，直接删掉。

## 推荐写法

写连续复盘段落时，优先保留用户的“前面做了什么 -> 现在还差什么 -> 这次接着补什么”的推进方式。不要改成标准文案式背景铺垫。

当段落只需要交代问题和动机时，用短句直说：

```text
Markdown 不能直接粘贴到公众号编辑器里用。
在线排版工具能转换，但通用模板我不喜欢。
我想做一套符合阿栩 IP 调性的排版主题。
```

不要扩写成：

```text
Markdown 适合写作、版本管理和 AI 修改，但真正发布时还需要富文本格式……
在线工具能解决格式问题，却解决不了风格问题……
IP 资产如果没有进入文章系统，就会停留在图片里……
```

这类解释看起来完整，但读者已经知道结论，继续解释只会显得死板。

使用具体转折：

- “我一开始以为只是要生成一张图，后来发现问题不是图，而是资产不稳定。”
- “这里我没有继续让 AI 自由发挥，而是先让它把判断标准写出来。”
- “这个名字不是 skill 起的。我是让 Codex 给了几个候选，最后自己选了这个。”

写实操时，优先使用：

```text
我当时的问题 -> 我怎么拆 -> 我保留了什么 -> 我踩了什么坑 -> 后来怎么改
```

写系列文章的承接段时，优先使用：

```text
前面我做了什么 -> 现在还差哪一步 -> 之前怎么处理 -> 为什么不合适 -> 这次打算怎么补
```

可接受的表达：

```text
前面我分享了如何将自己的公众号写作流程制作成 skill，并且优化了写作逻辑，蒸馏了对标账号的文章结构。

现在还差最后一步，将生成的 Markdown 格式文章，转成可以直接粘贴到公众号文章编辑器中的排版格式。

之前我是用在线工具转换的，能用，但是里面的模板我不是很喜欢，整体比较通用，也不符合阿栩的 IP 调性。

所以这次打算继续接入公众号文章排版 skill，定制一套专属风格的排版模板。
```

有真实对话时，使用对话块：

```text
我：帮我把这个技能安装到全局 https://github.com/...
Codex：...
```

真实对话缺失时，使用占位：

```text
[对话占位｜这里补真实 AI 对话]
建议补：用户原始指令、AI 的关键回复、用户如何确认或纠正。
```

## 避免

- 报告腔，例如“本文将从三个维度展开……”
- 空泛方法词，例如“赋能”“闭环”“降本增效”“生态化沉淀”，除非后面马上给出具体操作或证据。
- 用不同形容词重复同一个观点。
- 在展示真实过程前写很长的抽象解释。
- 对用户意图、结果或归因做没有证据的确定性判断。
- 仿写具名作者。
- 感想式、总结式、绕弯式废话，例如“这也是我这次最明显的感受”“会写每一个文件当然好，但更关键的是”“我最大的感受不是……而是……”“这也是我最想强调的一点”。
- 用“其实”“真正”“更重要的是”“这才是”“说白了”等词把普通判断包装成感悟。除非用户原文就是这种表达，否则删掉引导句，保留事实、动作和结论。
- 把用户直接推进式表达改成工整转场，例如“但真正准备发公众号时”“我发现还没闭环”“所以这次我想”“也就是说”“这样以后”。这类表达容易变成模板文案，优先保留用户原本的动作链。
- 只给专业名词，不解释它和当前案例有什么关系。
- 对普通事实做硬解释，例如把“Markdown 不能直接粘贴公众号”扩写成一段 Markdown 优点、富文本格式、在线模板局限和 IP 资产系统。能一句话说清的问题，不要写成完整论证。
- 把“完整展示流程”误当成“有价值”。没有具体启发的流程步骤应该压缩。

## 五个改稿测试

初稿、改稿和发布前都要过这五个测试。

### 1. 删减测试

这段删掉，文章是否损失信息、情绪、证据或认知推进？

如果不损失，删掉。不要因为它写得顺就留下。

### 2. 替换测试

这段能不能用更短、更具体的话说？

如果能，替换。优先保留事实、动作、判断和结果。

### 3. 出声测试

这段读出来像人在说话吗？

如果像在念报告，改成更直接的表达。不要只是加口语词，要补真实过程、判断或取舍。

### 4. So what 测试

读者看完这段会不会想“所以呢”？

如果会，说明这段没有写出和读者的关系。补读者收益、适用边界、下一步动作，或删除。

### 5. AI 味测试

检查是否存在：

- 安全但空泛的词。
- 对称但无信息的排比。
- 过度总结。
- 没证据的肯定判断。
- 把普通操作包装成方法论。

发现后直接改，不保留旧说法。

## 标题风格

生成标题和副标题时，要准确，不要夸大。

推荐：

- “我用 Codex 和 Moodboard Skill，做出了专属 IP 资产”
- “从审美对齐、角色生成到封面模板，一次把好看的图变成可复用资产”
- “前端工程师 8 个 Codex 检查项，先把 AI 改代码这件事做稳”
- “390px 页面被撑到 1284px：真正的问题不是 Tailwind”
- “这 6 个 Skill 到底适合谁：跑完一个真实任务后的结论”

避免：

- “震惊！AI 彻底改变公众号写作”
- “保姆级教程，手把手教你……”
- 声称 skill 完成了实际上由用户完成的决策
- 没有实测时写“必装、最强、直接复用”
- 没有筛选标准时写“N 个工具一篇收齐”

## 清单和素材包写法

清单文、提示词文、Skill / MCP 素材包要像可用资产，不要像资源搬运。

必须写清：

- 为什么选这些，不选那些。
- 每一项适合什么场景。
- 使用时要替换哪些变量。
- 怎么验证它真的有用。
- 不适合什么情况。

如果素材很多，宁可减少数量，也要保留筛选标准和使用边界。

## 用户改写处理

当用户说文章太板正时，不要只是加口语词。应该：

- 增加真实过程细节。
- 暴露不确定性和纠正过程。
- 用具体决策替换泛泛结论。
- 减少重复解释。
- 删除为了补齐逻辑而加的硬解释，尤其是读者不关心的背景、资产细节、概念优点和价值升华。
- 在有用的位置加入 AI 对话和截图。
- 删除“感受/启发/关键是”式过渡，把段落改成直接判断或具体动作。

当用户说“看不懂”“太抽象”“不像我的风格”“没有价值”时，先判断：

- 是否缺少真实场景或具体例子。
- 是否用了术语但没有解释。
- 是否在展示完整流程，而不是展示最有价值的关键步骤。
- 是否没有写出用户自己的判断、取舍和踩坑。
- 是否没有回答“读者看完能拿走什么”。

先修当前文章，再按 `memory-management.md` 判断是否进入长期规则候选。

## 风格候选记录示例

```markdown
## 可沉淀到 skill 的规则候选

- 规则：不要把普通操作包装成抽象方法论，优先保留用户真实判断和原话。
  来源：用户将“方法论式描述”改为“我当时其实没想那么复杂……”
  类型：写作风格
  适用范围：技术复盘、AI 工作流文章
  建议沉淀位置：references/writing-style.md
  状态：待用户确认
```
