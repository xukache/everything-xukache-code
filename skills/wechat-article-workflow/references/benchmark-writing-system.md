# 对标融合写作系统

本文件把已蒸馏的“智见AI x 韦东东 x 大前端架构师”方法接入公众号文章工作流。它只提供结构、节奏、解释、证据、清单资产和标题方法，不提供具名作者人格模仿。

## 不可违背项

- 只能写用户真实经历、真实项目和真实判断。
- 借鉴方法，不借作者人格、口头禅、私人经历和权威感。
- 没有实测，不写强推荐。
- 没有项目过程，不写企业级案例复盘。
- 没有筛选标准，不写大清单。
- 不编造客户、收入、指标、截图、失败经历或阅读数据。
- 用户自己的作者人设仍以 `author-persona.md` 为唯一来源。

## 先判断文章类型

在 `article-types.md` 判断写作任务后，再选择对标融合策略。

| 文章任务 / 外壳 | 主借鉴 | 辅借鉴 | 默认结构 | 必须有的证据 | 禁止 |
| --- | --- | --- | --- | --- | --- |
| 企业级案例复盘 / 技术复盘 | 韦东东 | 智见AI | 结果或问题 -> 场景约束 -> 技术链路 -> 决策点 -> 验证结果 -> 失败或边界 -> 可复用规则 | 真实过程、截图、指标、代码、失败点或选择理由 | 无项目证据时伪装成企业案例复盘 |
| 前端 / AI 编程事故复盘 | 大前端架构师 | 韦东东 | 现场数字 -> 看起来没问题 -> 真实根因 -> 分层拆解 -> 验证结果 -> 检查清单 | 真实事故、截图、代码、DevTools 数字、返工成本、PR/review 过程 | 没有现场和数字时制造翻车感 |
| 工程部署 / 复杂链路教程 | 韦东东 | 智见AI | 任务 -> 前置条件 -> 步骤 -> 示例输出 -> 常见坑 -> 验证方式 -> 下一步扩展 | 可复现步骤、命令、文件、预期输出和验证方式 | 只列命令，不解释场景和为什么 |
| 前端页面 / Prompt / Skill / MCP 教程 | 大前端架构师 | 智见AI | 场景 -> 可复制素材或步骤 -> 固定字段 -> 示例输出 -> 使用边界 -> 验证方式 | prompt、命令、配置、截图、页面结果、检查清单 | 只有素材，没有适用场景和验证方式 |
| 工具推荐 / 工具筛选 | 智见AI + 大前端架构师 | 韦东东 | 痛点 -> 推荐结论 -> 适用场景 -> 固定字段对比 -> 实测证据 -> 限制 -> 替代方案 | 使用过程、对比、成本、部署限制、失败案例或筛选标准 | 只写“好用、强、推荐” |
| 经验方法 / 工作流方法 | 智见AI + 大前端架构师 | 韦东东 | 具体问题 -> 方法命名或框架 -> 操作过程 -> 多场景例子 -> 边界 -> 迁移方式 | 真实项目、对话、文件、前后对比或工作体感 | 无证据上升到宏大趋势 |
| 观点判断 / 决策支持 | 智见AI + 大前端架构师 + 韦东东 | 按证据决定 | 判断 -> 具体事故/观察 -> 常见误区 -> 约束条件 -> 证据或反例 -> 新能力排序 -> 行动建议 | 反方观点、条件边界、案例或实测 | 尖锐但无条件边界，或制造无证据焦虑 |
| 提示词 / 指令 / 素材包 | 大前端架构师 | 智见AI | 场景集合 -> 每个场景的完整指令 -> 业务指标 / 画面 / 约束 / 避免项 -> 使用方式 -> 验证方式 | 可复制内容、生成结果、截图或测试输出 | 只有提示词，没有说明适用场景和验证方式 |
| 概念解释 | 智见AI | 大前端架构师 + 韦东东 | 读者困惑 -> 一句话定义 -> 类比或例子 -> 职业场景 -> 工程链路 -> 使用边界 | 当前案例、简化图示、流程或代码片段 | 只讲术语，不落到读者场景 |

## 融合规则

- 标题和开头借智见AI：清晰承诺、痛点前置、普通人能理解。
- 企业案例、工程链路、边界和 bad case 借韦东东：场景约束、技术链路、验证结果、失败案例和边界。
- 前端 / AI 实操、Skill / MCP / Prompt 清单、完整指令模板、AI 编程翻车复盘借大前端架构师。
- 每篇先选主参考账号，再按能力借其他账号；不要混成“既很炸、又很硬核、还全是清单”的平均风格。
- 解释时先让读者知道“为什么和我有关”，再进入“怎么实现”和“我能怎么做”。
- 结尾先收适用边界，再给下一步行动、检查清单或能力排序；不要只做口号式号召。
- 如果文章偏大众读者，降低术语密度，先写场景；如果文章偏技术读者，保留链路、配置、代码、prompt 和验证。

## 标题候选公式

- 结果 + 对象 + 场景：`从 X 到 Y：一个 Z 场景的全链路复盘`
- 冲突 + 判断：`别再只看 X，真正卡住的是 Y`
- 工具 + 边界：`X 到底适合谁：跑完 Y 场景后的真实结论`
- 数字 + 方法：`N 个 bad case 后，我重新设计了 X 流程`
- 前端对象 + 数量 + 可拿走资产：`前端工程师 N 个 X，帮你把 Y 做稳`
- 事故数字 + 根因：`X 页面被撑到 Y：真正的问题不是 Z`
- 热点 + 落地：`X 发布之后，企业 AI 应用真正该关注的是 Y`

使用这些公式时要降夸张强度。标题里的承诺必须能被正文证据兑现。

## 大纲必须写出的融合决策

大纲里增加一段“对标融合选择”：

- 文章类型判断：主任务、辅助任务、外壳。
- 主参考方法：智见AI、韦东东、大前端架构师，或按能力分工。
- 为什么这么选：对应读者状态和证据条件。
- 本文借什么：标题、开头、结构、解释、证据、结尾中的哪些部分。
- 本文不借什么：夸张标题、工程权威感、私人经历、客户案例、前端架构师身份、软考分支、未经验证的资源堆叠等。
- 证据门槛：至少一种硬证据，或明确标注缺失。

## 初稿写作门槛

- 前 300 字说明读者为什么要看。
- 每个关键判断都要有事实、过程、截图、代码、对话、配置、数字、失败案例或对比支撑。
- 至少写一个适用边界或不适用场景。
- 清单文必须有筛选标准；提示词 / 指令 / 素材包必须有使用场景和验证方式。
- 没有证据的强判断改成条件判断，或留为待补占位。
- 不把“完整流程”误当成文章价值；只展开能支撑主承诺的步骤。

## 纠偏

- 用户说“太像智见AI”：降低标题夸张度，保留清晰承诺，重写口吻和证据表达。
- 用户说“太像韦东东”：减少工程术语密度，前置读者痛点和通俗解释。
- 用户说“太像大前端架构师”：减少数量型标题和清单堆叠，保留具体场景和检查清单。
- 用户说“太虚”：补过程证据，删抽象判断。
- 用户说“太硬”：增加场景解释和读者收益，不删除核心证据。
- 用户说“像资源搬运”：补筛选标准、使用场景、实测证据和不适用边界。
- 用户说“不像我”：回到 `author-persona.md` 和用户原文，只保留对标结构方法。
