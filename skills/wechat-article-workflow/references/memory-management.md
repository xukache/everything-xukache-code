# 记忆管理

不要把每篇文章的所有修正都塞进 skill。记忆分两层管理。

## 长期 Skill 记忆

把稳定、重复出现的偏好放到 skill 的 references 中，尤其是 `writing-style.md`、`visual-workflow.md` 和本文件。

这些规则适用于后续多篇文章。

作者人设类规则优先写入 `author-persona.md`，普通写作口吻和反模式写入 `writing-style.md`。

## 写作人设蒸馏

长期写作风格不要只记录成形容词。参考 persona 类 skill 的思路，把用户反馈翻译成可执行的行为规则。

错误记录方式：

```text
用户喜欢通俗、有价值、有个人风格。
```

更好的记录方式：

```text
- 规则：解释抽象概念时，先用一句人话定义，再给类比或当前案例。
- 证据：用户说“抽象概念/专业名词要用类比或者举例子，让别人快速理解”。
- 写作表现：不要只写 Harness、Persona、蒸馏，要说明它在这篇文章里分别对应“生产线”“作者写作习惯”“从反馈里提炼规则”。
```

可蒸馏维度：

- 价值判断：用户认为什么内容值得写，什么只是凑完整。
- 解释方式：用户偏好类比、例子、操作步骤，还是理论定义。
- 文章人设：用户希望读者感受到怎样的作者形象。
- 取舍方式：用户如何决定保留、合并或删除章节。
- 纠错偏好：用户指出“不对”时，真正反对的是事实、结构、语气、术语，还是归因。

如果用户明确说“这是我个人写作风格”，通常应作为长期规则候选；用户确认或语义足够明确时，可以直接更新 `writing-style.md`。

## 单篇文章记忆

把文章特有状态放到该文章输出目录下。

推荐文件：

```text
article-handoff.md
revision-log.md
user-feedback.md
visual-plan.md
source-notes.md
```

示例：

- 本篇文章的最终标题。
- 本篇文章的图片列表。
- 本篇文章剩余的对话占位。
- 本篇文章已确认的归因边界。
- 本篇文章不要改动的文件。

这些不应该直接复制进 skill，除非它们能泛化。

## 提炼规则

完成一篇文章后，询问：

```text
这篇文章里的哪些修正规则应该沉淀成长期写作规则？哪些只属于本篇文章？
```

只有重复出现或明确可复用的规则，才提升到 skill 中。一次性的项目状态保留在文章目录。

## 触发时机

沉淀逻辑在以下时机触发：

1. 完整文章交付后
   - 已完成大纲、初稿、用户改写、标题、配图、目录整理和交接文档时，进入沉淀检查。

2. 用户多次纠正同类问题时
   - 例如“太板正”“不要只在会话输出”“原始素材要统一放文件夹”“不要乱归因”。
   - 这类规则看起来是长期偏好时，提示用户是否沉淀到 skill。

3. 用户明确说“以后都这样”时
   - 可以视为长期规则候选，但仍应说明将更新到哪个 reference 文件。

4. 生成单篇文章交接文档时
   - 在交接文档中增加：

```markdown
## 可沉淀到 skill 的规则候选
- 规则：
  来源：
  建议沉淀位置：
  是否需要用户确认：
```

5. 开始新文章前
   - 这不是沉淀，而是使用沉淀。开始新文章时读取长期规则，避免重复犯旧问题。

6. 用户提出修改建议后
   - 先完成用户要求的修改或回答。
   - 再判断这条建议是否只属于当前文章、是否需要写入本篇交接文档、是否属于长期规则候选。
   - 不要在执行修改前打断用户询问沉淀。

## 沉淀流程

不要直接把所有反馈写进 skill。按以下流程处理：

1. 先记录到当前文章的 `article-handoff.md`。
2. 标注它是“单篇状态”还是“长期规则候选”。
3. 向用户确认是否作为长期偏好。
4. 用户确认后，再更新对应 reference：
   - 写作口吻：`writing-style.md`
   - 作者人设、解释方式、长期表达习惯：`author-persona.md`
   - 配图规则：`visual-workflow.md`
   - 输出结构：`output-structure.md`
   - 工作流检查点：`workflow-checkpoints.md`
   - 记忆管理：`memory-management.md`
   - 发布检查：`review-checklist.md`
5. 更新后运行 skill 校验。

## 修改建议分流器

用户提出修改建议后，按四类分流。

### 1. 只属于当前文章，不沉淀

示例：

- “这篇文章标题改成 XXX。”
- “这张图放到第 07 节。”
- “这里补某个具体截图。”
- “这个项目里某个文件名写错了。”

处理：

- 只更新当前文章。
- 不询问是否沉淀。

### 2. 当前文章状态，写入 article-handoff

示例：

- “这篇文章不要动顶图和尾图。”
- “这篇文章封面不要插正文。”
- “这篇文章还有几处真实对话没补。”
- “这个命名是用户选的，不是 skill 生成的。”

处理：

- 写入本篇 `article-handoff.md`。
- 通常不询问是否沉淀，除非用户表达为长期规则。

### 3. 长期规则候选，写入 handoff 并在回复后询问

示例：

- “大纲不要只在会话里输出，要写文件。”
- “原始素材统一放 `raw-materials/`。”
- “用户修改建议要判断是否进入沉淀候选。”
- “不要把用户决策归因给 AI 或 skill。”
- “文章不能太板正，要有真实技术人复盘感。”

处理：

- 先完成当前修改。
- 写入本篇 `article-handoff.md` 的“可沉淀到 skill 的规则候选”。
- 在回复末尾简短询问用户是否确认沉淀到 skill。

### 4. 明确长期规则，建议直接更新 skill

示例：

- “以后都这样。”
- “默认都这么做。”
- “这个规则写进 skill。”

处理：

- 完成当前操作后，更新对应 reference。
- 运行 skill 校验。

## 判断维度

判断是否进入沉淀候选，看以下维度：

- 复用性：是否会影响后续多篇文章。
- 稳定性：是否是长期偏好，而不是当前文章特例。
- 流程性：是否影响写作流程、目录结构、配图流程或检查点。
- 风格性：是否影响长期写作口吻或反模式。
- 归因性：是否能避免以后错误归因。
- 风险性：如果不记录，下次是否容易重复犯错。
- 人设性：是否能帮助后续文章更像用户本人，而不是通用 AI 文案。

满足 2-3 个以上维度时，进入 `article-handoff.md` 的候选区。满足“复用性 + 稳定性 + 用户明显强调”时，才在回复末尾询问是否沉淀到 skill。

## 不打扰原则

以下情况不要询问沉淀：

- 只是改一句具体文案。
- 只是替换某张图。
- 只是当前文章的事实修正。
- 只是一次性的标题选择。
- 只是某个文件路径或截图位置。
- 用户明显在推进当前任务，而不是制定长期规则。

## 修改建议候选记录格式

```markdown
## 可沉淀到 skill 的规则候选

- 规则：
  来源：
  类型：输出结构 / 写作风格 / 配图流程 / 归因边界 / 检查点 / 其他
  适用范围：
  建议沉淀位置：
  状态：待用户确认
```

## 提示话术

当发现可沉淀规则时，可以这样问：

```text
这个反馈看起来不是只针对当前文章，而是长期写作偏好。我建议先写入本篇 article-handoff.md 的“可沉淀规则候选”，你确认后我再更新到公众号文章工作流 skill。
```

## 防污染规则

避免把过于具体的文章细节加入长期 skill 记忆，例如：

- 某篇文章的完整标题
- 某一张截图文件名
- 某个项目的临时文件夹
- 某个章节的一次性措辞偏好

拿不准时，先留在文章交接文档里。
