# 文档版本治理

本文件定义 `DEV_SPEC`、规格版本、架构版本和协作门禁的关系。固定七章读取 `references/dev-spec-fixed-outline.md`；模式推荐读取 `references/dev-spec-mode-selection.md`。

## 文档职责

| 文档或目录 | 保存内容 | 更新方式 |
|---|---|---|
| `DEV_SPEC.md` | 当前有效的开发规格、固定七章、规格级任务和验收 | 持续维护 |
| `docs/dev-spec/README.md` | 规格版本规则、索引、同步顺序和当前基线 | 持续维护 |
| `docs/dev-spec/versions/` | 已发布的独立规格基线增量 | 新基线发布后只读 |
| `docs/architecture.md` | 当前架构入口、阅读顺序和事实源优先级 | 持续维护 |
| `docs/architecture/<domain>.md` | 当前有效的主题架构事实 | 按架构变化更新 |
| `docs/architecture/versions/` | 完整架构快照、差异和迁移信息 | 架构版本发布后只读 |
| `docs/architecture/99-changelog.md` | 架构变化、影响和版本判定 | 以表格追加 |
| `docs/superpowers/specs/` | 单次设计确认记录 | 确认后原则上只读 |
| `docs/superpowers/plans/` | 已确认规格的实施计划 | 按计划范围维护 |
| `AGENTS.md` | 阅读入口、项目例外和强制门禁摘要 | 持续维护 |

职责边界：

- `DEV_SPEC.md` 是当前开发规格，不是代码实现清单。
- `docs/dev-spec/versions/` 记录规格基线，不替代当前规格。
- `docs/architecture/<domain>.md` 是当前架构事实，不是历史版本仓库。
- `docs/architecture/versions/` 是完整架构快照，不是单行 changelog。
- `docs/superpowers/specs/` 保存设计确认，不把设计讨论直接当作实现计划。
- `docs/superpowers/plans/` 只能描述已经确认的设计，不能反向决定架构。
- `AGENTS.md` 只做入口和摘要，详细事实必须链接到唯一来源。

## 三类版本的关系

开发规格版本、架构版本和产品发布版本相互独立：

```text
开发规格版本 != 架构版本 != 产品发布版本
```

### 开发规格版本

开发规格持续维护。只有出现可独立命名、可独立追踪或可独立验收的规格基线时，才在 `docs/dev-spec/versions/` 新增版本文件。

规格版本至少记录：

```text
版本标识
发布日期
关联 DEV_SPEC
新增或变更能力
范围与非目标
验收变化
文档影响
架构影响判定
关联设计确认
验证证据
```

### 架构版本

只有系统边界、数据所有权、公共契约、运行链路、部署拓扑或恢复方式发生架构级变化时，才创建 `docs/architecture/versions/<version>.md`。

架构版本必须保存：

```text
完整架构快照
相对上一版本的差异
兼容性影响
迁移或恢复要求
关联开发规格版本
受影响的架构分册和契约
验证证据
```

不能只保存一张新图、一个 diff 或一段 changelog 作为完整架构版本。

### 产品发布版本

产品发布版本由发布流程管理。它可以包含多个规格或架构变更，也可能只包含实现、修复或文档变化。不能用产品版本号替代规格版本或架构版本。

## 变化判定矩阵

先识别原始变化，再分别判断五类对象是否更新。`架构 changelog` 是变化记录，不等于完整架构版本。

| 变化类型 | `DEV_SPEC.md` | 规格版本 | 当前架构分册 | 架构 changelog | 完整架构版本 |
|---|---:|---:|---:|---:|---:|
| 错别字、链接、非语义表达 | 更新 | 否 | 按影响 | 按影响 | 否 |
| 同一主题内的小节确认 | 更新 | 否 | 按影响 | 是 | 否 |
| 新增独立能力或验收口径 | 更新 | 是 | 按影响 | 是 | 按边界判断 |
| 改变模块职责、依赖或运行链路 | 更新 | 是 | 更新 | 是 | 是 |
| 改变数据所有权、持久化或恢复方式 | 更新 | 是 | 更新 | 是 | 是 |
| 新增外部接口或部署方式 | 更新 | 是 | 更新 | 是 | 是 |
| 只调整文档组织、阅读顺序或链接 | 按需 | 否 | 按需 | 是 | 否 |
| 只调整实施步骤且不改变规格 | 否 | 否 | 否 | 否 | 否 |

判定细则：

1. “文件发生变化”不等于“架构发生变化”。
2. 新增独立能力即使代码量很小，也不能只在当前 `DEV_SPEC.md` 写一行并丢失规格基线。
3. 改变模块职责、依赖方向、数据所有权或运行调用链，必须创建完整架构版本。
4. 只调整入口导航时，最多追加表格 changelog，不发布完整架构版本。
5. 无法判断时标记“待确认”，不能通过延后版本目录或重排文档掩盖不确定性。

## 架构 changelog

`docs/architecture/99-changelog.md` 使用表格追加，不覆盖历史记录。最低表头为：

```text
日期 | 类型 | 变更内容 | 影响文档 | 是否改变架构边界
```

每行应补充关联规格、影响范围、版本结论和验证证据。导航调整也可以记录，但必须明确标记为文档组织变化。

## 固定同步顺序

所有规格或架构变化按以下顺序处理：

```text
识别原始变化
  -> 判断是否改变项目事实
  -> 更新 DEV_SPEC.md
  -> 用户或治理门禁确认
  -> 判断是否形成独立开发规格基线
  -> 判断是否改变架构边界
  -> 更新当前架构分册
  -> 追加架构 changelog
  -> 必要时发布开发规格增量版本
  -> 必要时发布完整架构版本
  -> 创建或更新实施计划
  -> 实现与验证
  -> 回写任务状态、证据和实际结果
```

说明：

- 纯文档导航任务也使用独立任务分支，但不修改实施任务状态。
- 计划只能在规格和设计确认后创建。
- 代码实现不能先于已确认的规格和模块设计。
- 版本判定应在实施前完成；不能等到发布后统一补齐。
- `DEV_SPEC.md`、当前架构分册和 changelog 可以持续更新，但历史版本文件不得原地覆盖。

## 只读与历史保护

已发布的规格版本和架构版本默认只读：

- 不把当前内容覆盖到历史版本文件。
- 不重写历史版本的日期、版本标识、差异或验证证据。
- 发现历史版本错误时，追加更正记录或创建新版本，不静默改写。
- 旧文档仍可能被代码、测试或部署配置引用时，不得直接删除。
- 移动、删除、归档或改为只读必须经过用户确认，并保留迁移映射。

不存在独立基线时，不创建空版本目录、空版本文件或只有标题的版本占位物。

## 完整模式治理级别

完整模式支持三个固定治理级别：

| 级别 | 允许动作 | 完成和集成门禁 |
|---|---|---|
| `strict` | 读取、审计、起草和在确认后的实现 | 用户确认后才能标记完成、提交和合并 |
| `reviewed` | 可提交并创建 PR | PR 评审通过后才能标记完成；评审前不得宣称完成 |
| `autonomous` | 验证通过后可自动更新状态和合并 | 必须满足项目配置的验证、审计和回滚门禁 |

规则：

- `strict` 是完整模式默认值。
- 项目必须在 `AGENTS.md` 和 `DEV_SPEC.md` 中明确当前治理级别。
- 执行 Agent 不得因为时间压力、用户催促或测试通过临时改变治理级别。
- 治理级别与 DEV_SPEC 模式分开记录；`reviewed` 不是轻量模式，`autonomous` 也不是不启用。

## Git 分支与任务边界

项目配置至少包含：

```text
integration_branch: <architecture | develop | main | custom>
task_branch_pattern: task/<task-id>-<slug>
one_task_per_branch: true
```

默认规则：

- 每个任务从最新集成分支创建独立任务分支。
- 一个任务分支只承载一个规格级任务。
- 纯文档治理、依赖维护或版本治理任务也使用独立分支。
- 纯文档治理任务不得修改 DEV_SPEC 实施任务状态。
- 未达到当前治理级别的门禁前，不勾选任务完成、不提交、不合并。
- 未经用户明确确认，不合并或推送到 `mvp`、`main` 或其他非配置分支。

## 轻量模式升级

轻量模式不建立版本目录，但必须使用固定七章和稳定编号。出现以下任一信号时，提示升级为完整模式：

- 开始分阶段或多版本交付。
- 出现多个相互依赖的任务。
- 新增公共 API、事件、持久化、迁移或兼容性要求。
- 系统边界、数据所有权或部署方式开始变化。
- 多人或多 Agent 并行协作。
- 需要恢复历史决策或严格验收证据。

升级流程：

```text
审计当前轻量 DEV_SPEC
  -> 补齐完整模式必选小节
  -> 用户确认当前完整规格
  -> 建立规格版本治理入口
  -> 将当前规格登记为首个规格基线
  -> 配置 governance_level 和 integration_branch
  -> 补充阶段、任务、证据和分支规则
  -> 判断是否需要首个架构版本
```

升级不得：

- 创建与旧规格平行的第二份完整规格。
- 删除或覆盖已有轻量规格。
- 重新编号固定七章或条件小节。
- 因升级本身自动发布架构版本；架构版本仍按实际边界判断。
- 在用户确认升级前创建实施代码或标记任务完成。

## 已有项目保护

已有项目先形成文档和事实地图：

```text
现有文档
  -> 当前事实源
  -> 历史记录
  -> 重复内容
  -> 冲突内容
  -> 过期候选
```

处理顺序：

1. 读取并列出事实来源及引用关系。
2. 区分当前实现、目标设计、历史协议和待确认内容。
3. 建立保留、迁移、归档和删除候选清单。
4. 将冲突和删除候选交给用户确认。
5. 迁移到唯一事实源后，再执行去重或删除。

不能把新模板当成高于代码、测试、部署配置或已确认项目事实的来源。
