# DEV_SPEC 模式选择

本文件只负责判断是否启用 DEV_SPEC、推荐哪一种模式，以及如何保留用户的最终选择权。固定七章读取 `references/dev-spec-fixed-outline.md`；规格和架构版本读取 `references/document-version-governance.md`。

## 使用时机

完成项目分类和已有文档初步审计后读取本文件。读取顺序固定为：

1. 识别项目生命周期、系统边界、协作、契约、验收和演进风险。
2. 给出三档模式和当前推荐。
3. 明确推荐理由、不会创建的内容和治理停止点。
4. 请求用户确认最终模式。
5. 只有确认后，才读取固定目录或版本治理 reference，并建立对应文档。

不能根据文件数量、项目语言、存在数据库或“正式项目”单个信号静默选择模式。

## 三档模式

### 完整模式

适用于长期维护、多个模块、公共契约、数据迁移、异步运行时、权限隔离、多 Agent 协作、多阶段交付、架构恢复或需要历史追踪的项目。

必须产出或接入：

- 当前完整 `DEV_SPEC.md`。
- 固定七章和固定小节编号。
- 规格确认记录、规格级任务、任务状态和验证状态。
- 开发规格版本治理。
- 当前架构事实源、架构 changelog 和按需完整架构版本。
- 分支、评审、提交、合并和文档同步门禁。

不会自动创建：

- 未经确认的业务需求、模块实现或代码目录。
- 没有独立基线的空版本目录或空版本文件。
- 不适用的架构、API、部署或观测分册。
- 独立的 `docs/agent-monitoring.md`。

完整模式默认使用 `strict` 治理级别；项目已有明确配置时，可以保持 `reviewed` 或 `autonomous`，但必须记录配置来源。

### 轻量模式

适用于中小项目：模块数量有限，但需要统一目标、范围、验收标准和完成门禁；当前没有明显的迁移、公共边界演进或复杂协作风险。

必须产出或接入：

- 单文件 `DEV_SPEC.md`。
- 固定七章和固定小节编号。
- 仅启用必选和直接相关的条件小节。
- 规格级任务、验收标准和任务状态/验证状态分离。
- 明确不适用项和待确认项。

默认不会创建：

- `docs/dev-spec/versions/` 规格版本目录。
- `docs/architecture/versions/` 完整架构版本目录。
- 没有真实领域的架构或 API 分册。
- 多 Agent、迁移、复杂观测和多环境治理。

轻量模式不是“随便写一个 README”。它仍然要维护完整七章的稳定编号，并在范围和验收发生变化时更新 `DEV_SPEC.md`。

### 不启用

适用于单次、小范围、短生命周期、单一边界的工作，且已有可靠的需求、架构或工程事实源可以指导实施。

处理方式：

- 继续使用现有 `AGENTS.md`、架构、API 契约和工程文档流程。
- 不创建 `DEV_SPEC.md`。
- 不创建规格版本目录。
- 不创建架构版本。
- 仍遵守已有项目的确认、测试、提交和合并门禁。

不启用 DEV_SPEC 不等于跳过基础事实源。若项目缺少基础文档，仍按项目分类补齐必要的 `AGENTS.md`、`docs/architecture.md`、`docs/api-contracts.md` 或对应工程规范。

## 六维风险矩阵

每个维度记录“观察到的事实、风险等级、对模式的影响”。只写“复杂”或“简单”不足以形成推荐依据。

| 维度 | 低风险信号 | 高风险信号 | 对模式的影响 |
|---|---|---|---|
| 生命周期 | 一次性交付、短期验证、无后续版本 | 长期维护、分阶段交付、多个版本或恢复计划 | 长期维护倾向完整；短期工作可不启用 |
| 系统边界 | 单页面、单模块、单一运行入口 | 多模块、前后端、运行时、异步、外部系统或权限域 | 边界越多，越需要固定规格和架构追踪 |
| 协作复杂度 | 单人、单分支、无评审 | 多人、多 Agent、任务分支、PR、逐项确认或严格门禁 | 协作越复杂，越倾向完整模式 |
| 契约风险 | 无公开接口、无持久化、无迁移 | 公共 API、数据模型、兼容性、迁移、事件或外部集成 | 强契约、迁移或兼容风险直接推荐完整模式 |
| 验收复杂度 | 单一手工检查、已有明确验收事实 | 多层测试、真实场景、性能、安全、可靠性或多阶段验收 | 验收轨道越多，越需要规格级验收映射 |
| 演进风险 | 边界稳定、无需历史追踪 | 模块职责可能调整、架构恢复、版本对比或历史协议仍有效 | 需要历史追踪时推荐完整模式 |

### 风险判定规则

使用以下规则，而不是给六个维度简单计数：

1. 任何强契约、数据迁移、架构边界变化、恢复要求或高协作门禁，至少推荐完整模式。
2. 多个维度同时达到中高风险时，推荐完整模式，即使当前代码量很小。
3. 少量模块、存在公共接口且需要统一范围和验收，但没有明显迁移或架构演进风险时，推荐轻量模式。
4. 单次、小范围、短生命周期、单一边界且已有明确事实源时，推荐不启用。
5. 用户要求“正式项目”“以后可能扩展”“先别问”不能替代风险事实，也不能取消模式确认。

## 推荐与确认协议

模式判断结果必须同时包含以下内容：

| 项目 | 必须说明 |
|---|---|
| 项目分类 | 项目形态、阶段和已有文档状态 |
| 风险事实 | 六维中实际观察到的事实和风险 |
| 三档选择 | 完整模式、轻量模式、不启用 |
| 当前推荐 | 只能有一个明确推荐 |
| 推荐理由 | 将风险事实连接到推荐，而不是只说项目大小 |
| 产出边界 | 会创建什么、不会创建什么 |
| 治理停止点 | 用户确认前允许做什么，禁止做什么 |
| 用户选择 | 明确请求用户最终选择，可接受推荐、改选或暂缓 |

固定提示模板：

```text
根据当前项目事实，我识别出以下六类风险：
- 生命周期：<事实与风险>
- 系统边界：<事实与风险>
- 协作复杂度：<事实与风险>
- 契约风险：<事实与风险>
- 验收复杂度：<事实与风险>
- 演进风险：<事实与风险>

可选模式：
1. 完整模式：<产出与适用边界>
2. 轻量模式：<产出与适用边界>
3. 不启用：<保持现有事实源与边界>

当前推荐：<模式>。
推荐理由：<把风险事实连接到结论>。
在你确认前，我只执行<允许的审计/读取动作>，不会<禁止的文档、代码、状态或版本动作>。
请确认最终选择：采用推荐模式、改选另一模式，还是暂缓决定？
```

推荐结果不是用户确认。用户说“开始”“确认文档”“先写代码”但没有明确选择模式时，仍停在模式选择门禁。

## 已有模式的处理

S05-S09 这类场景已经给出当前模式时，不要因每个任务重新静默切换模式：

- 明确识别并保持当前模式。
- 只有发现真实升级信号时，才重新展示三档选择。
- 版本变化、评审压力或用户催促不能被用来偷偷降低治理级别。
- `strict`、`reviewed`、`autonomous` 是治理级别，不是 DEV_SPEC 模式；两者分别记录。

对于已有完整模式，推荐表述应明确为：

```text
当前继续使用完整模式。本次变化是否新增规格版本或架构版本，另按版本治理矩阵判定。
```

## 轻量模式升级

出现以下任一信号时，必须提示可能从轻量模式升级为完整模式：

- 新增多个核心模块或新的运行时边界。
- 引入公共 API、事件、数据迁移或兼容性要求。
- 出现多人、多 Agent、任务分支、PR 或逐项确认。
- 需要分阶段交付、历史追踪、架构恢复或跨版本比较。
- 验收从单一检查扩展为多层测试、性能、安全或可靠性门禁。

升级原则：

1. 保留现有 `DEV_SPEC.md` 和已有事实。
2. 不创建平行的第二份完整规格。
3. 按固定七章启用新增条件小节。
4. 保留已有小节编号；未启用的小节保留编号空缺。
5. 根据实际边界判断是否建立首个规格基线或架构版本。
6. 升级本身先经过用户确认，再读取固定目录和版本治理 reference。

## 禁止行为

- 静默启用完整模式、轻量模式或不启用。
- 以项目大小、文件数量、语言或“正式项目”为唯一依据。
- 用推荐代替用户最终选择。
- 在模式确认前创建 `DEV_SPEC.md`、规格版本、架构版本、实现代码或任务状态。
- 把实施计划当作未确认规格或架构的替代物。
- 为了“看起来完整”创建空版本目录、空版本文件或不适用分册。
- 将轻量模式升级为完整模式时重新编号或删除旧事实。
