# DEV_SPEC 固定七章

本文件定义 `DEV_SPEC.md` 的稳定目录。章节名称、顺序、小节名称和编号固定；模式只决定哪些小节启用，不改变编号。

## 全局规则

### 固定编号

顶层章节固定为：

1. 项目概述
2. 核心能力与设计原则
3. 技术与工程决策
4. 测试与验收
5. 系统架构与模块设计
6. 实施路线与进度
7. 演进路线与已知限制

固定编号的作用是保持链接、任务追溯、评审记录和 Agent 协作稳定。不得因为项目简单、升级模式或新增条件小节而重新编号。

### 必选与条件小节

- 必选小节始终生成；信息不足时写明“待确认”，不能静默删除。
- 条件小节按项目分类、真实边界和当前阶段启用。
- 条件小节未启用时保留编号空缺，后续小节继续使用原编号。
- 不适用小节写“不适用：<原因>”或在目录中明确标记“未启用：<原因>”，不能把编号分配给其他主题。
- 轻量模式只启用必选和直接相关条件小节；完整模式按确认结果启用全部相关小节。
- 不启用 DEV_SPEC 时不生成本目录，但项目仍可使用其他标准架构和工程文档。

### 章节边界

- 第一章回答为什么做、做什么和不做什么。
- 第二章回答能力如何被使用以及必须遵守的设计原则。
- 第三章记录技术选择和待决策项，不把未确认方案写成事实。
- 第四章记录验收轨道、证据和完成门禁。
- 第五章记录逻辑边界、依赖、数据和运行时，不让物理目录反向决定架构。
- 第六章记录规格级任务和阶段，不写具体类、函数或测试节点。
- 第七章记录未来方向和限制，不把未确认演进项当作当前承诺。

## 第一章：项目概述

| 编号 | 小节 | 启用规则 | 本节职责 |
|---|---|---|---|
| 1.1 | 项目定位 | 必选 | 用一句话说明项目是什么、服务谁、解决哪类问题 |
| 1.2 | 背景与问题 | 必选 | 说明现状、触发原因和要解决的问题 |
| 1.3 | 用户、调用者与使用场景 | 条件 | 存在明确用户、调用者、角色或使用流程时启用 |
| 1.4 | 项目目标与成功标准 | 必选 | 定义可观察目标、成功信号和不以代码完成代替的结果 |
| 1.5 | 当前范围 | 必选 | 列出当前版本包含的能力、边界和交付范围 |
| 1.6 | 非目标 | 必选 | 明确当前不做的能力，防止实现过程中范围膨胀 |
| 1.7 | 约束与假设 | 必选 | 记录环境、依赖、时间、合规、资源和待确认假设 |
| 1.8 | 阶段成果 | 完整模式 | 记录阶段性规格、文档、验证和交付成果 |

本章禁止写入：

- 尚未确认的模块职责、类设计或目录结构。
- 具体实施步骤、代码任务或函数清单。
- 把未来路线写成当前范围。

| 2.3 | 关键用户或调用流程 | 条件 | 存在用户流程、调用链或多步交互时启用 |
| 2.4 | 质量属性 | 必选 | 记录可用性、可维护性、性能、安全、可靠性等适用质量目标 |
| 2.5 | 设计原则 | 必选 | 记录必须长期保持的边界、优先级和取舍原则 |
| 2.6 | 可扩展与可替换性 | 条件 | 存在插件、适配器、供应商或未来替换需求时启用 |
| 2.7 | 可观测与可解释性 | 条件 | 存在 Agent、异步流程、复杂决策或诊断要求时启用 |
| 2.8 | 能力边界与降级策略 | 条件 | 存在外部依赖、局部失败、降级或人工接管时启用 |

核心能力逐项说明固定使用以下视角：

```text
问题
调用者
输入
处理
输出
失败与边界

验收入口
```

本章禁止把技术选型、物理目录、类函数设计或未确认架构方案伪装成能力定义。

每项技术决策至少包含：

```text
当前选择

替代方案
适用边界
已知限制
重新评估时点
```

“待决定”必须明确影响，不得用占位符掩盖阻塞项。第三章不直接冻结未确认的实现细节。

## 第四章：测试与验收

| 编号 | 小节 | 启用规则 | 本节职责 |
|---|---|---|---|
| 4.1 | 测试目标与验收原则 | 必选 | 说明测试证明什么、不证明什么，以及验收优先级 |
| 4.2 | 测试分层 | 必选 | 说明单元、集成、契约、端到端和人工验证的边界 |
| 4.3 | 验证轨道 | 必选 | 将功能、文档、接口、架构、性能或安全验证分轨记录 |
| 4.4 | 测试替身与外部依赖边界 | 条件 | 存在模型、数据库、网络、队列或第三方服务时启用 |
| 4.5 | 功能与测试映射 | 必选 | 将能力、验收标准和测试证据建立追溯关系 |
| 4.6 | 用户场景与端到端验收 | 存在用户流程时 | 记录真实场景、前置条件、动作、结果和证据 |
| 4.7 | 验收证据规则 | 完整模式 | 记录日志、截图、报告、哈希、版本和人工确认要求 |
| 4.8 | 性能、安全与可靠性基线 | 存在相应风险时 | 记录指标、边界、故障和安全验收基线 |
| 4.9 | 测试执行与 CI | 存在工程基线时 | 记录命令、环境、触发方式、失败处理和产物 |
| 4.10 | 完成门禁 | 必选 | 记录设计、实现、验证、评审、用户确认和集成门禁 |

任务状态与验证状态必须分离：

```text
任务：[ ] 未开始 | [~] 进行中 | [x] 已完成 | [!] 阻塞
验证：PASS | FAIL | BLOCKED | NOT RUN
```

完成门禁不能由“测试通过”单独替代。完整模式下，规格确认、模块设计确认、匹配验证、评审和用户确认分别记录。

本章禁止：

- 用测试数量代替验收结论。
- 把未运行的验证写成 PASS。
- 把任务状态 `[x]` 当作验证状态。
- 把实施计划中的测试节点直接复制成规格级验收标准。

## 第五章：系统架构与模块设计

| 编号 | 小节 | 启用规则 | 本节职责 |
|---|---|---|---|
| 5.1 | 整体架构图 | 必选 | 展示系统边界、主要层次、外部依赖和核心调用方向 |
| 5.2 | 逻辑分层与依赖方向 | 必选 | 定义层次职责、允许依赖、禁止反向依赖和适配器边界 |
| 5.3 | 模块职责与边界 | 必选 | 定义模块负责什么、不负责什么、输入输出和协作边界 |
| 5.4 | 核心数据模型与所有权 | 存在状态或持久化数据时 | 定义数据实体、所有者、生命周期和一致性边界 |
| 5.5 | 核心数据流与调用链 | 必选 | 说明请求、事件或任务如何在模块间流动 |
| 5.6 | 公共契约与接口边界 | 存在模块或外部接口时 | 定义公共类型、API、事件、错误和兼容边界 |
| 5.7 | 运行时、状态与生命周期 | 存在异步、状态机或长流程时 | 定义创建、运行、取消、恢复、完成和失败传播 |
| 5.8 | 权限、安全与隔离边界 | 存在权限、租户或敏感数据时 | 定义身份、授权、隔离、审计和最小权限 |
| 5.9 | 错误、事件与可观测性 | 后端或复杂项目 | 定义错误分类、事件、日志、指标、追踪和诊断 |
| 5.10 | 部署拓扑与外部系统 | 存在部署或外部依赖时 | 定义进程、队列、数据库、模型、网络和运行拓扑 |
| 5.11 | 物理目录与公开入口 | 工程结构已确认时 | 记录已确认的目录、入口和模块映射 |
| 5.12 | 待确认的架构决策 | 必选 | 列出未决边界、影响、候选方案、确认人和截止条件 |

架构建模顺序固定为“先逻辑边界、后物理目录”：

```text
逻辑边界
  -> 依赖方向
  -> 数据与调用链
  -> 公共契约
  -> 运行与部署边界
  -> 物理目录与公开入口
```

改变模块职责、依赖方向、数据所有权、公共契约、运行链路或部署边界时，完整模式必须同步规格版本、当前架构分册、架构 changelog，并按版本矩阵判断是否创建完整架构版本。

本章禁止：

- 让物理目录、现有类名或代码布局反向决定逻辑边界。
- 用架构图替代文字事实源、接口契约或版本记录。
- 在用户确认前把待确认设计写成最终架构。
- 为了补齐视觉结构创建没有事实内容的架构分册。

## 模式启用摘要

| 模式 | 章节规则 | 版本和协作规则 |
|---|---|---|
| 完整模式 | 逐章确认；启用全部适用条件小节；未适用编号保留空缺 | 启用规格版本、架构治理、任务证据和协作门禁 |
| 轻量模式 | 整体确认；只启用必选和直接相关条件小节 | 单文件 DEV_SPEC；不建立空版本目录；升级时保持编号 |
| 不启用 | 不生成 DEV_SPEC | 继续现有标准文档流程，不创建 DEV_SPEC 版本对象 |

完整模式逐章确认的停止点是：当前章内容、启用的小节、待确认项和本章不适用项均已得到用户确认。轻量模式的停止点是：整份单文件规格及其启用范围得到用户确认。

## 章节变更门禁

修改 `DEV_SPEC.md` 前记录：

```text
本次影响章节
本次影响小节
是否启用新的条件小节
是否保持既有编号
是否改变逻辑边界
是否触发规格版本
是否触发架构版本
用户确认记录
```

如果无法判断是否影响架构边界，先标记“待确认”，不能通过重排章节或新增实施任务绕过判断。
